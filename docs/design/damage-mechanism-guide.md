## 设计摘要（先看这 10 条）

1. **白板环境**：60 级首领、1 级基础防御 60（60 级 952.8）、抗性 0、失衡易伤倍率 1.5。
   防御区 `794/(952.8+794)=0.4545…`，失衡区 2.5，抗性区 1.0。见 §17。
2. **三层模型**：局外面板 → 局内修正 → 事件结算。音擎 `[局内生效]`、影画、4 件套
   都进第二层，**不进面板接口**。见 §18。
3. **音擎特效要进武器库**：`effect.targets[].perRefinement` 存 5 档数组，不线性外推。
   例：涅槃初翎「破壳日」异常精通 90/99/108/117/126，火伤 40/44/48/52/56。见 §23.4。
4. **每个代理人一份数据档案**：`strategy/<slug>/calculator/calculator.json`；
   共享引擎、私有档案，档案之间不继承。**不建议** 61 份计算代码。见 §19。
5. **理论循环**：事件序列 + 技能倍率（从 `<slug>.json` 解析）+ 异常触发次数假设；
   不模拟积蓄过程。见 §20。
6. **词条最优分配**：两阶段束搜索 + 局部搜索；约束必须包含「4 条 × 9 档 × 单条 ≤6」
   的每盘可行性，否则会给出刷不出来的 `AM 27 + ATK% 27`。见 §21。
7. **驱动盘评分**：`w_i = D(n+e_i) − D(n)`，单盘分 `100 × Σ r_i w_i / (6w1+w2+w3+w4)`。
   「双爆分」对纯异常角色是 0，不要用通用分。见 §22。
8. **相对值基准**：`C0R1 = 100%`；同时给 `samePanel`（隔离物品）与 `optimalPanel`
   （实际养成）。菲欧妮示例：满精双生 2 层 83.57%，4 层 96.81%。见 §23。
9. **非满配**：同样 30 条，分配不同可差 1–2 个百分点；`drop` 曲线 77.28%，
   攻略页现有 30 条 75.98%，满配 100%。见 §24。
10. **落地顺序**：先修 `MAIN_STAT_EXCLUDES` / `armorer` 命名等阻断，再做效果层，
    3 个试点（叶瞬光 / 菲欧妮 / 克拉蕾），P2 接命破般岳，最后铺开 61 人。
    见 §27 / §28；任务级计划见 [damage-solving-engine.md](../plans/damage-solving-engine.md)。

## 0. 三条伤害路径（先记住这个）

绝区零的伤害有三条**完全不同的乘区链**，不能混用：

| 路径 | 公式 |
| --- | --- |
| **常规伤害** | 基础伤害区 × 增伤区 × 暴击区 × 防御区 × 抗性区 × 减易伤区 × 失衡易伤区 × 特殊乘区 |
| **贯穿伤害**（命破） | 基础伤害区 × 增伤区 × 暴击区 × **贯穿增伤区** × 抗性区 × 减易伤区 × 失衡易伤区 × 特殊乘区 |
| **异常伤害** | 基础伤害区 × 增伤区 × **异常精通区** × 防御区 × 抗性区 × 减易伤区 × 失衡易伤区 × **伤害等级区** × **异常增伤区** × **异常暴击区** |

**五条容易做错的归属规则**：

1. 增伤区分四类：常规增伤区 / 贯穿增伤区 / 异常增伤区 / 直接攻击增伤区**互不稀释**。
2. 增伤区是**加算区**：同区内相加后再乘；跨区才相乘。
3. 增伤区也能减伤：「造成的伤害降低 X%」属于**增伤区**，不是减易伤区。
4. 异常不吃暴击区：异常伤害用**异常暴击区**（异常暴率 × 异常暴伤），不是常规暴击区。
5. 贯穿不吃防御区：贯穿伤害用**贯穿增伤区**替代防御区。

## 1. 基础伤害区

```
基础伤害区 = Σ(伤害倍率 × 对应属性)
攻击力 = [基础攻击力 × (1 + 局外攻击力%) + 局外数值攻击力] × (1 + 局内攻击力%) + 局内数值攻击力
```

| 类型 | 基础属性 | 备注 |
| --- | --- | --- |
| 常规伤害 | 攻击力 | |
| 贯穿伤害（命破） | **贯穿力** | `贯穿力 = 0.3 × 攻击力 + 0.1 × 生命值上限`，所有命破代理人统一 |
| 锐化伤害（锋御） | **防御力** | 锋御的直伤统称锐化伤害，把攻击力换成防御力；锋御音擎基础属性无一例外是基础防御力 |
| 真实伤害 | 目标最大生命值 | 只算基础伤害区，部位破坏的伤害属于这类 |

> 命破 / 锋御的**异常伤害仍用攻击力**——只有直伤换口径，异常伤害照旧。
> 命破无视 100% 防御：贯穿伤害的防御区乘数恒为 1.000。

> 游戏里伤害显示**向上取整**，多段伤害逐段取整再相加。

## 2. 增伤区

```
增伤区 = 1 + Σ(增伤)      有效范围 [0, 6]
```

来源：属性增伤（元素限定）、技能类型增伤、攻击类型增伤、全类型增伤，以及「造成的伤害降低」。

- 属性增伤共 7 种（火 / 电 / 冰 / 物理 / 以太 / 烈霜 / 玄墨），但**只有火、电、冰、物理、以太 5 种**进增伤区；烈霜按冰、玄墨按以太结算。
- 「追加攻击」类效果除自身标签外，还带来源的技能类型与攻击类型标签。
- 描述像「易伤」的效果（如朱鸢的[以太余烬]）**仍然进增伤区**。

## 3. 暴击区 / 异常暴击区

```
暴击区：   暴击时 1 + 暴击伤害；   未暴击时 1
暴击期望 = 1 + 暴击率 × 暴击伤害
异常暴击区：暴击时 1 + 异常暴击伤害；期望 1 + 异常暴击率 × 异常暴击伤害
```

| 项 | 范围 |
| --- | --- |
| 暴击率 | [0, 1]（锋御可超 100%） |
| 暴击伤害 | [0, 5]（即 500%） |
| 暴击区 | `[1, 6]`（**当前引擎**把暴伤 clamp 到 500%） |

> 旧版本文写的是 `[1, 10]`，与 `zones.py::crit_zone()` 不一致：后者把暴伤 clamp 到
> `5.0`，因此期望暴击区最大是 `1 + 1 × 5 = 6`。本文按**代码**改为 `[1, 6]`；
> 若官方实际允许更高的暴伤上限，应**先改 clamp 再改本行**，不要只改文档。

代理人基础暴击率 5%、基础暴击伤害 50%；敌人基础暴击率 0、基础暴击伤害 50%。

## 4. 防御区

```
防御区 = 攻击方等级基数 / (受击方有效防御 + 攻击方等级基数)

受击方有效防御 = 受击方防御 × (1 − 攻击方穿透率%) − 攻击方穿透值      # 下限 0
受击方防御 = (基础防御 × (1 + 初始防御%) + 初始固定防御) × (1 + 防御加成% − 防御降低%)
```

对敌简化：

```
敌人有效防御 = 基础防御 × (1 + 防御加成% − 防御降低% − 无视防御%) × (1 − 穿透率%) − 穿透值
```

| 有效范围 | 防御区 (0, 1]，游戏内可达下限 0.0283；有效防御 ≥ 0 |

**两条必须记住的算术关系**：
- **无视防御与减防加算**，**穿透率与减防乘算**——两者不是一回事。
- 减防是敌人身上的 debuff（全队吃），无视防御是技能级的；数值上等价。

**锚点数值**：

| 项 | 值 |
| --- | --- |
| 攻击方等级基数 | 60 级及以上恒为 **794** |
| 60 级打 60 级以上首领的默认防御区 | `794 / (952.8 + 794) = 0.4545` |
| 1 级基础防御 | 普通 36~46、精英 45~54、杜拉罕 58、首领 60（→ 60 级 952.8） |

## 5. 抗性区

```
抗性区 = 1 − 受击方抗性 + 受击方抗性降低 + 攻击方无视抗性      有效范围 [0, 2]
```

- 敌人的**弱点属性抗性 = −0.2**（抗性区 1.2）、**抗性属性抗性 = +0.2**（抗性区 0.8）。
- 霜寒与玄墨没有独立抗性，按冰 / 以太结算。
- 抗性是**按属性**的。

## 6. 异常侧乘区

```
异常精通区 = 异常精通 / 100                          # 有效范围 [0, 10]
伤害等级区 = trunc(1 + (等级 − 1) / 59, 4)          # 1 级 = 1，60 级 = 2
异常增伤区 = 1 + Σ(异常增伤)                        # 属性异常 / 紊乱 / 异放 / 乱流，相加
异常掌控区 = 异常掌控 / 100                          # 向下取整；有效范围 [0, 3]
异常暴击区 = 暴击 1 + 异常暴伤；期望 1 + 异常暴率 × 异常暴伤
异常积蓄值 = 基础异常积蓄值 × 异常掌控区 × 异常积蓄效率区 × 异常积蓄抗性区 × 距离衰减区
异常积蓄效率区 = 1 + 异常积蓄效率提升 + 异常积蓄值提升 − 异常积蓄效率降低
异常积蓄抗性区 = 1 − 异常积蓄抗性 + 异常积蓄抗性降低
```

- **异常掌控必须向下取整**（不是四舍五入）。
- 「异常积蓄效率提升」与「异常积蓄值提升」是**同一个效果**。
- 异常积蓄**不随等级成长**，基础积蓄值几乎独一无二，**一般只能查表**。
- 触发阈值与敌方等级无关，只与**等阶**（普通 / 精英 / 首领）和**已触发次数**有关：普通 : 精英 : 首领 = 4 : 15 : 20，物理异常阈值是其他属性的 1.2 倍。

### 6.1 紊乱倍率（按基底异常）

紊乱的**伤害倍率** = `450% + 时间项`，按基底异常分五类。
`t` 是基底异常的**已流逝时间**（秒），`10 − t` 是基础持续时间 10 秒下的剩余时间：

| 类别 | 基底异常 | 属性 | 固定倍率 | 时间项 | 时间步长 |
| --- | --- | --- | ---: | --- | ---: |
| 持续伤害类 | 灼烧 | 火 | 450% | `floor((10 − t) / 0.5) × 50%` | 0.5s |
| 持续伤害类 | 感电 | 电 | 450% | `floor(10 − t) × 125%` | 1s |
| 持续伤害类 | 侵蚀 | 以太 | 450% | `floor((10 − t) / 0.5) × 62.5%` | 0.5s |
| BUFF 类 | 霜寒 | 冰 | 450% | `floor(10 − t) × 7.5%` | 1s |
| BUFF 类 | 畏缩 | 物理 | 450% | `floor(10 − t) × 7.5%` | 1s |

记 `T = 10 − t`（剩余时间），时间项可以写成：

```text
火：floor(T / 0.5) × 50%
以太：floor(T / 0.5) × 62.5%
电：floor(T) × 125%
冰 / 物理：floor(T) × 7.5%
```

**四条不能混的边界**：

1. `t` 是**基底异常**从施加到触发紊乱的**已流逝时间**，不是紊乱自己的持续时间；
   `T = 10 − t` 是触发瞬间的**剩余时间**。乱流表（§12）用的是 `T`；
   不要把 `t` 直接代进乱流公式，也不要把 `T` 当 `t`。
2. `10` 是**基础持续时间**。若持续时间被延长（例如菲欧妮 C2 的灼烧 +2 秒），
   用**有效持续时间**替换 `10`，并把 `t` 夹在 `[0, 有效持续时间]`；
   事件存储**不得按基础时长截断**（§16.5）。
3. 本表只给**伤害倍率**。紊乱的**失衡倍率恒为 200%**（§10）是另一件事；
   不要用 450% 去算失衡值。
4. 本表只列 5 类基底；**烈霜 / 玄墨的紊乱倍率未给出**，不要臆造 0，
   按官方后续数据补。紊乱伤害的其它乘区（异常增伤 / 异常暴击）仍按 §6 与
   各代理人 calculator 配置处理，不要用这张表替代乘区归属。

> 例：灼烧在 `t = 2s` 时触发紊乱 → `floor((10−2)/0.5) = 16`，
> 倍率 = `450% + 16 × 50% = 1250%`；感电在 `t = 2s` → `floor(8) = 8`，
> 倍率 = `450% + 8 × 125% = 1450%`。

## 7. 减易伤区 / 失衡易伤区

```
减易伤区 = 1 + 受击方易伤 − 受击方减伤      有效范围 [0.2, 2]
失衡易伤区 = 失衡时 1 + 失衡易伤倍率；未失衡时 1 + 未失衡倍率
```

| 乘区 | 有效范围 |
| --- | --- |
| 减易伤区 | [0.2, 2]（叠减伤到不了无伤） |
| 失衡易伤区（失衡时） | [0.2, 5] |
| 失衡易伤区（未失衡时） | [1, 3] |

敌人失衡易伤倍率默认 25% / 50% / 100% 三种。代理人和邦布**没有失衡条**，敌人打它们时**不计失衡易伤区**。

> **B 部分的白板环境把失衡易伤倍率锁定为 150%**（区 `1 + 1.5 = 2.5`），且所有事件都按
> 「失衡中」结算。这不改变「默认敌人 25/50/100」这条游戏事实，只是**比较口径**；
> 代价是冲击力 / 失衡效率类收益在本口径下恒为 0，无法评价。详见 §17。

## 9. 特殊乘区（距离衰减区）

距离衰减区同时影响**伤害、失衡值、异常积蓄值**三者：

- **默认型**：与敌人距离超过 15m 时伤害衰减 25%，之后每远 5m 再衰减 25%。
- **格莉丝型**：超过 15m 时衰减 30%。
- 已有类型：默认型、格莉丝型、扳机型、耀嘉音型。

## 10. 失衡

```
失衡值累积 = Σ(基础失衡区) × 失衡抗性区 × 失衡值提升区 × 受到失衡值提升区 × 距离衰减区

基础失衡区   = 冲击力 × 失衡倍率                    # 冲击力有效范围 [0, 1000]
失衡抗性区   = 1 − 受击方失衡抗性                   # 有效范围 [0, 2]
失衡值提升区 = 1 + 造成失衡值提升 − 造成失衡值降低   # 有效范围 [0, 4]
受到失衡值提升区 = 1 + 受到失衡值提升 − 受到失衡值降低 # 有效范围 [0, 4]
```

- 弱点属性的失衡抗性 −20%（→ 1.2）、抗性属性 +20%（→ 0.8）。
- **紊乱失衡倍率恒为 200%**；紊乱失衡 = 上式 × 失衡等级区，`失衡等级区 = 1 + 0.0075 × 等级`。
  这是**失衡值**的倍率，不是紊乱伤害倍率；伤害倍率见 §6.1（450% + 时间项）。
- 6 号位「冲击力」主词条是提升失衡值的渠道之一。

## 11. 锋御（锐化伤害 / 锐化增伤 / 锐暴伤害）

| 结构 | 规则 |
| --- | --- |
| 锐化伤害 | 用**防御力**作为基础属性，乘区构成与常规伤害相同 |
| 锐化增伤 | **独立乘区**（约 10%），与常规增伤区**独立计算** |
| 锐暴伤害 | 暴击时不用暴击伤害结算，而用**锐暴伤害**（基础 150%）；暴击率可超 100%，超出部分再判定一次锐暴 |

暴击区的平方项结构（`k = 1 + 锐暴伤害`）：

```
暴击一次 → k
暴击两次 → k²
期望：暴击率 ≤ 100%  →  c × k
      暴击率 > 100%  →  k × [1 + (c − 1) × k]
```

- 锐暴伤害**无法通过驱动盘词条堆**。
- 暴击率上限 **200%**。
- 转模比例：initialCritDmgToCritRateRatio，逐角色可配（克拉蕾 0.35）。
- 锐能不吃驱动盘 6 号位的能量自动回复加成。

## 12. 风属性（风化 / 浸染 / 乱流）

| 状态 | 机制 |
| --- | --- |
| 风化 | 风属性异常的基础状态：积蓄满后打断敌人行动并造成一段风属性伤害 |
| 浸染 | 敌人处于风化时，用火 / 冰 / 电 / 物理 / 以太攻击触发对应属性的浸染，提升风属性与该属性的直接伤害。一次风化期间最多触发一次浸染 |
| 乱流 | 替代紊乱的新异常结算：风化与另一种异常同时存在时**不触发紊乱，改触发乱流**；乱流结算风化之外的另一种属性异常，造成范围异常伤害 |

乱流倍率表（按非风基底异常分）：

| 基底 | 固定倍率 | 时间项 |
| --- | ---: | --- |
| 强击（物理） | 800% | floor(T) × 7.5% |
| 碎冰（冰） | 1300% | floor(T) × 7.5% |
| 灼烧（火） | 900% | floor(T / 0.5) × 50% |
| 感电（电） | 650% | floor(T) × 125% |
| 侵蚀（以太） | 650% | floor(T / 0.5) × 62.5% |
| 烈霜 | 0% | floor(T) × 75% |

> 这里 `T` 是**剩余时间**；紊乱表（§6.1）里的 `t` 是**已流逝时间**，`T = 10 − t`。
> 两者不要混用。乱流是「替代紊乱」的结算路径，不是紊乱的变体。

## 13. 局内 / 局外，与快照 / 实时

```
战斗白值 = 局外白值 + 局外绿值
攻击力 = [基础攻击力 × (1 + 局外攻击力%) + 局外数值攻击力] × (1 + 局内攻击力%) + 局内数值攻击力
```

**积蓄时加权**（一次算定）：攻击力、增伤、等级、穿透率、穿透值、异常精通、失衡值提升

**结算时实时**（打到的瞬间读）：抗性、抗性降低、防御降低、无视防御、无视抗性、失衡易伤、异常增伤、异常暴击

> 无视防御与无视抗性**不进加权**。

来源快照的精确分界：
- **自身作为来源**：实时读取面板
- **外部来源**（队友 / 外部快照）：使用冻结快照，优化期间固定
- **敌人防御 / 抗性 / 事件失衡状态**：始终实时
- **等级 / 核心技等级**：当前等级必须覆盖存量事件里的等级快照

## 16. 补充机制（来自 zzz_calculator 参考实现）

以下机制在《数据机制导论》与底层机制系列中未完整展开，以 `zzz_calculator` 的现行建模为准。
对应规格见 `docs/design/damage-formulas.md` §3.11 / §3.13。

### 16.1 异放（Release）机制

异放不是一种独立伤害类型，而是**异常结算路径**：把原异常的结算倍率转换为另一套倍率。

- **来源 / 触发者分离**：异放从**原异常来源**的实时数据或外部冻结快照继承异化；**触发者侧不得重复乘算**异化乘区。即使异化有效值为 0 也要显示。
- **两种倍率模式**：
  - `originalAnomalyRatio`：最终倍率 = 原异常单次倍率 × 公式值
  - `fixedAnomalyMultiplier`：最终倍率 = 公式值
- **公式叶节点**：常量 / 触发者属性（局外或局内面板）/ 核心技倍率 / 是否失衡条件 / 异放精通收益修正（`releaseProficiencyYieldBonus`）。
- **单位**：`raw` / `percent` / `decimal` 三档，`percent` 时除以 100。
- **触发者属性白名单**：`atk` / `anomalyProficiency` / `anomalyMastery`，面板可选局外或局内。
- ** Velina（维琳娜）异放**：强制使用风化基底，通过 `releaseSource` 选择 `micro_vortex` / `broad_vortex` / `ultimate_wind`；不再携带通用 `triggerActorRef` / `anomalySource`；异放来源 Buff 继承时**排除**六影的动态增伤。
- **冻结快照**：外部来源使用冻结快照（含角色、配置哈希、捕获时间、面板、修正参数），优化期间固定，刷新才更新；**不得实现 A+B 联合驱动盘搜索**。
- **异放精通收益修正**：`modifierFactor = 1 + bonus`，中性时（≈1）在乘法公式中不显示。

### 16.2 潜能影像（Potential Vision）

- 角色可配置 `potentialVision`，含 `maxLevel`（0~6）与 `scaling.levels` 表。
- **异常精通 → 平 ATK 转换**（Jane 机制）：在战斗中，将最终异常精通按一定比例转换为局内固定攻击力加成，转换发生在伤害公式之前；异常精通转异常暴击率则作为事件修正，不改变面板暴击率。
- `requirement.minPotentialLevel / maxPotentialLevel` 控制规则是否激活；潜能材料化在面板/事件编译前过滤不活跃规则。
- P0 兼容值为 0 时，只要结构化 scaling 源存在即合法。

### 16.3 影画（Cinema）等级

- `defaultCalculationConfig` 是作者内容，不是模拟。
- Cinema 分辨率：选择**不高于**所选等级的最大配置阈值；匹配潜能变体优先于 Cinema 变体。
- 当前构筑技能等级为最终等级，**不重复加** Cinema 等级。
- `defaultTeammates` 仅在角色无已保存的队友选择或显式 Buff 选择时生效，按作者 Cinema 等级选择两位队友及其 Buff；已保存的空选择也具权威性。

### 16.4 维琳娜（风属性）专属

- **能量自动回复转换**：按每个候选盘的最终局外面板计算，不读局内能量回复，不能在候选面板出现前预编译为 0；转换后的异常掌控再进入异常精通与异放评价。
- **六影「风化重施增伤」**：运行时输入 0%~40%（默认 40%），存为 `anomalyDamageBonus`，**只命中**属性异常 `wind_corrosion`；与 C2 及专武风化增伤**相加**，不作用于普通直伤、风直伤易伤、乱流、紊乱、异放或耀变。
- **队友 Buff 四项**：F 级核心固定 `+150%` 乱流倍率；额外能力 `+10%` 乱流增伤；1 影 `20%` 全属性抗性无视；2 影 `+15%` 乱流增伤。核心队友 Buff 固定 F 级，不跟随维琳娜核心等级。
- **异放来源**：`micro_vortex` / `broad_vortex` / `ultimate_wind`，强制风化基底。

### 16.5 事件存储约束（实现纪律）

- 乱流事件**只保存**非风基底异常、已流逝时间、次数、失衡状态；**不保存**风化来源、第二异常来源、来源面板快照、剩余时间或待确认倍率。
- 事件存储**不得按基础时长截断**（最终计算可能叠加持续时间延长）。
- 异放事件不携带通用 `triggerActorRef` / `anomalySource`（Velina）；通用 Aria/Vivian 双来源模型保留。

## 17. 标准白板环境（Whiteboard Target）

### 17.1 一句话定义

**60 级代理人打 60 级首领：无抗性、无弱点、无易伤、无减伤、无距离衰减，
失衡易伤倍率锁定 150%，所有事件按「失衡中」结算。**

这是一个**比较基准**，不是对某个具体 Boss 的描述。它的价值在于：
所有配装、影画、音擎都在同一个「干净」的敌人身上比较，差异只来自配装本身。

### 17.2 参数表

| 参数 | 值 | 说明 |
| --- | ---: | --- |
| `id` | `whiteboard-boss-60` | 数据集里的稳定 id |
| `level` | 60 | 攻击方与受击方都按 60 级 |
| `baseDefense` | 60.0 | **1 级基础防御**（首领档），不是 60 级实际防御 |
| `defense` | 952.8 | `60 / 50 × 794`，见 §3.4 |
| `attributeResistance` | **0.0** | 无抗性、也无弱点 |
| `staggerResistance` | **0.0** | 失衡抗性中性 |
| `stunVulnerability` | **1.5** | 失衡易伤**倍率** 150% → 区 `1 + 1.5 = 2.5` |
| `unstunnedStunVulnerability` | 1.0 | 未失衡时倍率 100% → 区 2.0；本口径不用 |
| `easyDamage` | 0.0 | 无易伤 |
| `damageReduction` | 0.0 | 无减伤 |
| `defenseBonus` | 0.0 | 无防御加成 |
| `fixedDefense` | 0.0 | 无固定防御 |
| `distanceFalloff` | 1.0 | 关闭距离衰减（近战贴脸） |
| `stunned` | `true` | **所有事件**按失衡中读取 |

派生常量：

```text
攻击方等级基数 = 794
基础防御（60 级首领） = 60 / 50 × 794 = 952.8
防御区 = 794 / (952.8 + 794) = 0.4545454545…
抗性区 = 1 − 0 + 0 + 无视抗性 = 1 + 无视抗性
减易伤区 = 1
失衡易伤区 = 1 + 1.5 = 2.5
特殊乘区 = 1
常数 K = 0.4545454545… × 1 × 2.5 = 1.1363636363…
```

> **K 只对绝对伤害有意义。** 比较两套配装时，K 在分子分母同时出现，可以约掉；
> 但报告里的「总伤」必须乘上它，否则数字比游戏内小一半以上。

### 17.3 为什么抗性是 0，不是 −0.2

「无弱点」= **没有弱点属性**，所以抗性取中性的 `0`，不是弱点属性的 `−0.2`。

| 目标 | 抗性 | 抗性区 | 对「无视抗性 15%」的相对收益 |
| --- | ---: | ---: | ---: |
| 弱点 Boss | −0.2 | 1.2 | `1.35 / 1.2 = +12.5%` |
| **白板 Boss** | **0.0** | **1.0** | `1.15 / 1.0 = +15.0%` |
| 抗性 Boss | +0.2 | 0.8 | `0.95 / 0.8 = +18.75%` |

弱点会把「无视抗性」的相对收益压低（因为基数已经是 1.2），抗性会抬高。
白板的 `0` 是**中性基准**：既不让所有伤害凭空 ×1.2，也不让无视抗性显得过强。

同理，**无抗性**不等于「抗性 −20%」；它只是没有正抗性。

### 17.4 为什么锁定 150% 失衡易伤

150% 是用户指定的比较口径，含义是：

- 所有伤害事件都发生在**失衡窗口**内，`Z_stun = 2.5`；
- 不建模「失衡覆盖率」，也不建模「打多少秒失衡 / 多少秒非失衡」；
- 冲击力、失衡效率、失衡持续时间类收益在本口径下**恒为 0**，不参与排序。

这不是说这些属性没用，而是说**这个口径不评价它们**。
如果某个配装的核心卖点是「更快打进失衡」，它会被本口径低估；这类问题应另开
「失衡覆盖率」目标，而不是偷偷改 `stunVulnerability`。

> **对相对值的影响**：`Z_stun = 2.5` 是常数，会在所有配装间约掉。
> 只有当某个效果**改变失衡易伤倍率本身**（例如叶瞬光核心被动的「失衡易伤上限」、
> 某些影画的「失衡易伤 +X%」）时，它才进入相对值。这类效果必须单独建模为
> `stunDmgMultiplierBonus`，不能混进普通增伤区。

### 17.5 白板目标的数据形状

建议在 `backend/src/zzz_panel/core/damage/targets.py` 新增：

```jsonc
{
  "id": "whiteboard-boss-60",
  "name": "白板 60 级首领（无抗性 / 无弱点 / 失衡 150%）",
  "level": 60,
  "baseDefense": 60.0,
  "attributeResistance": 0.0,
  "staggerResistance": 0.0,
  "stunVulnerability": 1.5,
  "unstunnedStunVulnerability": 1.0,
  "easyDamage": 0.0,
  "damageReduction": 0.0,
  "defenseBonus": 0.0,
  "fixedDefense": 0.0,
  "distanceFalloff": 1.0,
  "stunnedDefault": true
}
```

与现有 `STANDARD_TARGET` 的差异：

| 字段 | `STANDARD_TARGET`（现状） | 白板目标 | 备注 |
| --- | ---: | ---: | --- |
| `attribute_resistance` | −0.2（弱点） | **0.0** | 现状是「弱点 Boss」，不是白板 |
| `stagger_resistance` | 0.2 | **0.0** | 弱点才 −20% 失衡抗性，白板中性 |
| `stun_vulnerability` | 1.0 | **1.5** | 现状按 100% 倍率 |

| `distance_falloff` | 1.0（在 `RealtimeReadings`） | 1.0 | 建议收进目标，单一真源 |

> **不要直接改 `STANDARD_TARGET`。** 它已被 `damage-formulas.md` 的 C01 契约钉在
> `0.4545`，而且它的抗性 −0.2（弱点）已被现有报告使用；白板是**新增目标**，不是替换。
> 需要「弱点 / 抗性」对照时，用 §17.6 的敏感性目标。

### 17.6 敏感性目标（可选，不作为标题口径）

| 目标 | 抗性 | 失衡倍率 | 用途 |
| --- | ---: | ---: | --- |

## 18. 从面板到局内伤害：三层模型

### 18.1 三层，不要混

```text
┌──────────────┐   ┌──────────────────┐   ┌──────────────────┐
│ ① 局外面板    │ → │ ② 局内修正        │ → │ ③ 伤害结算        │
│ out-of-combat│   │ in-combat effects │   │ damage events     │
└──────────────┘   └──────────────────┘   └──────────────────┘
 基础 + 音擎基础    音擎被动 / 4 件套      乘区 × 倍率 × 事件次数
 + 核心 + 主词条    影画 / 潜能 / 队友      → 单事件伤害 / 总伤害
 + 副词条 + 2件套   条件 / 层数 / 覆盖率
```

| 层 | 输入 | 输出 | 现在的代码 |
| --- | --- | --- | --- |
| ① 局外面板 | 基础面板、音擎二元组、核心两槽、4/5/6 主词条、副词条条数、2 件套 | `atk / hp / def / cr / cd / dmg / pr / pv / am / ac / imp / er` | `core/panel.py`（三方对拍锁定） |
| ② 局内修正 | ① 的 totals + 音擎被动、4 件套、影画、潜能、队友、条件 | 战斗白值 + `SnapshotReadings` / `RealtimeReadings` | **缺**：需要新的 `core/damage/effects.py` |
| ③ 伤害结算 | ② 的读数 + 事件（路径 / 倍率 / 标签）+ 目标 | 单事件伤害、逐乘区明细、总伤害 | `core/damage/engine.py` |

**为什么必须分开**：

- 面板是**局外静态**的，三方对拍锁的是它；把音擎被动塞进面板，会让「毕业面板」
  变成「某个覆盖率假设下的面板」，不可复现；
- 音擎被动、影画、4 件套大多是**条件触发**的，有层数、持续时间、覆盖率；
  它们不应该改变「面板有多少攻击力」，而应该改变「进战斗后攻击力乘多少」；
- 分开之后，同一份局外面板可以配不同的局内假设，做敏感性分析。

### 18.2 白板口径下的公式链

把 §17 的常数代进 §1–§7：

```text
战斗攻击力 = [基础攻击力 × (1 + 局外攻击力%) + 局外数值攻击力]
             × (1 + 局内攻击力%) + 局内数值攻击力

常规直伤（单事件） =
  倍率 × 战斗攻击力
  × (1 + Σ增伤)                 # 含属性增伤、技能增伤、音擎/影画增伤
  × Z_crit                       # 期望 1 + 暴击率 × 暴击伤害
  × Z_def                        # 794 / (有效防御 + 794)
  × Z_res                        # 1 + 无视抗性（白板抗性 0）
  × Z_vuln                       # 1
  × Z_stun                       # 2.5
  × Z_special                    # 1（关闭距离衰减）

异常伤害（单事件） =
  异常倍率 × 战斗攻击力
  × (1 + Σ增伤)
  × (异常精通 / 100)
  × Z_def
  × Z_res
  × Z_vuln
  × Z_stun                       # 2.5
  × 伤害等级区                   # 60 级 = 2.0
  × (1 + Σ异常增伤)
  × Z_anomaly_crit               # 期望 1 + 异常暴率 × 异常暴伤
```

其中：

```text
Z_def = 794 / (max(0, 952.8 × (1 − 减防% − 无视防御%) × (1 − 穿透率%) − 穿透值) + 794)
```

> **命破的直伤**把 `Z_def` 换成 `1`（无视 100% 防御），基础属性换成贯穿力；
> **锋御的直伤**把基础属性换成防御力，暴击区换成锐暴平方项。
> 异常伤害始终用攻击力，且始终有防御区——不要因为角色是命破/锋御就把异常也换口径。

### 18.3 局内修正的数据模型：`Effect`

局内效果统一成一条可审计的记录，不要让每个代理人自己发明字段：

```jsonc
{
  "id": "weapon.ep-2259.passive.fire_dmg",
  "source": { "kind": "weapon", "id": "ep-2259", "refinement": 1 },
  "scope": "self",
  "label": "破壳日 · 火属性伤害",
  "target": "dmg",
  "kind": "pct",
  "value": 40,
  "damageType": "fire",
  "phase": "in_combat",
  "readout": "per_path",
  "condition": { "kind": "any_ally_anomaly_crit" },
  "duration": 20,
  "refresh": true,
  "stacks": { "max": 1, "default": 1, "expected": 1 },
  "uptime": 1.0,
  "status": "modeled",
  "notes": "队伍中任意角色对敌人造成的属性异常伤害产生暴击时触发；示例按 100% 覆盖。"
}
```

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| `source.kind` | `weapon` / `set4` / `cinema` / `core` / `potential` / `team` / `field` | 来源归属；决定「谁能吃到」 |
| `scope` | `self` / `team` | v1 只支持 `self`；`team` 需要冻结快照，见 §28.3.4 |
| `target` | `atk_pct` / `atk_flat` / `hp_pct` / `def_pct` / `cr` / `cd` / `dmg` / `am` / `pr` / `pv` / `anomaly_dmg` / `anomaly_crit_rate` / … | 落到哪个累加器 |
| `kind` | `pct` / `flat` / `base` | 与规则表一致：`base` 并入基础值 |
| `value` | 数值 | 与 `perRefinement` / `perStack` 二选一 |
| `damageType` | `all` / `fire` / `ice` / … / `anomaly` / `direct` / 技能标签 | **按事件过滤**，防止火伤加成打到物理事件 |
| `phase` | `in_combat` / `out_of_combat` | 本设计里音擎被动/影画/4 件套都是 `in_combat`；`out_of_combat` 只留给「必须在面板前生效」的少数数据 |
| `readout` | `per_path`（默认）/ `snapshot` / `realtime` | `per_path` = 直伤实时、异常积蓄时；只有明确只进一侧时才写另外两个。见 §18.5 |
| `condition` | 枚举 / 小型 DSL | `always` / `any_ally_anomaly_crit` / `on_special` / `enemy_under_state` / `enemy_stunned` / … |
| `stacks` | `max` / `default` / `expected` / `perStack` | 层数；`expected` 是期望层数（可小数），默认等于 `default` |
| `uptime` | 0~1 | 覆盖率；默认 1.0 只用于「文档已明确常驻」的效果 |
| `status` | `modeled` / `partial` / `descriptive` | **不允许静默为 0**；未建模必须显式标出 |

精炼/影画成长不要写公式，写**数组**：

```jsonc
{
  "target": "am",
  "kind": "flat",
  "perRefinement": [90, 99, 108, 117, 126],
  "perStack": false
}
```

> 参考实现与官方文案都出现过**非线性**的精炼阶梯（例如 30/34/38/42/48），
> 线性外推会在 R3/R4 悄悄算错。数组长度为 5，`R1` 取 `[0]`，`R5` 取 `[4]`。

### 18.4 效果的应用顺序

固定顺序，任何一步都不能跳：

1. **局外面板**：`core/panel.py` 算出 totals（不含任何条件效果）。
2. **局内百分比/固定值**：先把 `atk_pct` / `atk_flat` / `hp_pct` / `def_pct` 作用到
   战斗白值；再算派生值：
   - 命破：`贯穿力 = 0.3 × 战斗攻击力 + 0.1 × 战斗生命值`；
   - 锋御：`实际暴击率 = 面板实际暴击率 + Σ(cr 效果)`；`cd` 效果**不**进转模。

   > 这两个派生值必须在局内效果之后**重算**；不要直接拿面板 `mode_stats` 的
   > `penforce` / `actual_cr` 当最终值。面板只给「无局内效果」的基准。
3. **局内加法属性**：`cr` / `cd` / `dmg` / `am` / `pr` / `pv` / `anomaly_crit_*`。
4. **按事件过滤**：对每个事件，把 `damageType` 匹配的 `dmg` / `anomaly_dmg` 加起来；
   不匹配的不加。**不要先算一个全局增伤再给所有事件用。**
5. **构造读数**：`SnapshotReadings`（攻击、增伤、等级、穿透率、穿透值、异常精通、
   失衡值提升）与 `RealtimeReadings`（抗性、减抗、减防、无视防御、无视抗性、
   失衡易伤、异常增伤、异常暴击）。
6. **逐事件结算**：`compute_damage()`；同一次循环内的事件伤害**相加**，不是相乘。

### 18.5 快照 / 实时的落地边界

| 事件路径 | 攻击/增伤/精通/穿透 | 抗性/减防/无视防御/失衡易伤/异常暴击 |
| --- | --- | --- |
| 直伤 | 命中瞬间实时 | 命中瞬间实时 |
| 异常 | **积蓄时加权**（一次算定） | **结算时实时** |
| 紊乱 / 乱流 / 异放 | 结算时按各自来源 | 结算时实时 |

因此同一个 `Effect` 在不同路径下可能读不同侧。`Effect.readout` 默认写 `per_path`：
直伤实时、异常积蓄时；只有「明确只影响一侧」的效果才写死 `snapshot` 或 `realtime`。

- 「装备者造成的火属性伤害提升 40%，持续 20 秒」——直伤在命中时读；
  异常在**积蓄时**读；如果 Buff 是在积蓄之后才触发，本次异常**不吃**。
- 「无视 15% 抗性」——结算时实时；不进积蓄加权。
- 影画「对灼蚀敌人伤害 +30%」——直伤实时；异常积蓄时读；覆盖率是假设。

> 实现上不要把 `Effect` 只应用到一个 `CombatPanel` 就完事；要给
> `SnapshotReadings` 与 `RealtimeReadings` **分别**生成两份读数。
> 这正是 `engine.py` 把两者拆成两个 dataclass 的原因。

### 18.6 当前实现的缺口（必须先补）

| 缺口 | 现状 | 影响 |
| --- | --- | --- |
| 音擎被动 | `weapons.json` 只有 `base` + `substat`；`refresh_weapon_presets.py` 抓了 `multi_table` 但只取面板 | 所有音擎只剩「基础值 + 固定副词条」，被动全丢；专武与下位的差距算不出来 |
| 4 件套 | `drive-discs.json` 有 `setEffect4` 文本，但计算器只建模 2 件套 | 影画/音擎对比时套装收益不全 |
| 影画 | `<slug>.json` 只有文本；没有结构化效果 | 无法算 0→6 影 |
| 潜能 | 仓库里**没有**结构化的潜能数据（攻略文本里可能有描述） | 依赖潜能的角色面板/伤害缺一块 |
| 队伍 | 没有队友 Buff 数据集 | 只能做单人白板 |
| 技能倍率 | `score_build(multiplier=1)` | 只能比排序，不能出绝对伤害 |
| 异常参数 | 没有基础积蓄/异常倍率/异常暴击来源 | 异常循环只能按假设 |
| 事件过滤 | `DamageInput` 只有一个 `damage_bonus` | 属性增伤会打到不匹配的事件 |

> 这张表就是 §26 数据管线与 §27 落地清单的依据。

## 19. 代理人计算器：目录、契约与互不兼容

### 19.1 先给结论：每个代理人一份**数据档案**，不是一份代码

用户提出的「各计算器互不兼容、放在各自 strategy 文件夹」方向是对的，但
**「互不兼容」应该落在数据上，不是代码上**：

- 真正因人而异的是：循环、技能倍率、效果归属、阈值假设、影画/音擎的触发条件；
- 真正必须共享的是：乘区公式、面板公式、快照规则、取整/钳制规则。

如果 61 个代理人各有一份 `calc.py`，那么：

1. 公式改一次要改 61 处，必然漂移；
2. 测试无法保证「同一个乘区在 61 份代码里一致」；
3. 跨代理人比较失去意义（同一个音擎在不同代码里可能算法不同）；
4. 新代理人只能靠复制，错误会一起复制。

所以推荐：

```text
共享引擎（1 份，backend/src/zzz_panel/core/damage/）
   ↑
代理人档案（61 份，strategy/<slug>/calculator/calculator.json）
   ↑
生成物（61 份，report.json）
```

**互不兼容的边界**：`calculator.json` 只对自己的 `agentId` 有效；引擎在加载时
硬校验，拒绝把 A 的档案套到 B 上。档案之间不继承、不共享默认值、不互相 import。
引擎是共享的，但**档案是私有的**。

### 19.2 推荐目录

```text
strategy/<slug>/
├── data/
│   ├── <slug>.json              # 抓取产物（原文，不改）
│   └── <slug>.strategy.json     # 攻略编辑内容（页面渲染）
└── calculator/
    ├── calculator.json          # ★ 唯一入口：循环 / 效果 / 假设（人工维护）
    ├── README.md                # 订正说明：每个数字从哪来（可选）
    ├── rotation.md              # 循环依据：技能顺序、次数、为什么（可选）
    └── report.json              # 生成物：相对值表 / 曲线 / 评分（不手改）
```

为什么放 `calculator/` 而不是塞进 `data/`：

- `data/` 的契约是「抓取产物 + 页面编辑内容」，渲染器只读它；
- `calculator/` 是**工具链**的输入，不参与页面首屏渲染；
- 两者生命周期不同：`data/` 随 Wiki 刷新，`calculator/` 随机制理解更新。

### 19.3 `calculator.json` 契约

```jsonc
{
  "schemaVersion": 1,
  "engineVersion": ">=1.0 <2.0",
  "slug": "phoenix",
  "agentId": "ep-2216",
  "agentName": "菲欧妮·蕾法爱菈",
  "calculatorKind": "personal",
  "roleScope": "anomaly",
  "status": "complete",
  "damageModel": "mixed",            // 直伤 + 属性异常；相对值示例按纯异常口径（§23.6）
  "target": "whiteboard-boss-60",
  "baseline": {
    "cinema": 0,
    "weaponId": "ep-2259",
    "refinement": 1
  },
  "build": {
    "core": ["ac", "atk_base"],
    "sets": { "set4": "ep-191", "set2": "ep-1194" },
    "mainStats": {
      "disc4": "am_92",
      "disc5": "dmg_30",
      "disc6": "ac_pct_30"
    },
    "dmgElement": "fire",              // 5 号位属性伤害 / 属性 2 件套的元素
    "substatBudget": 54,
    "substatCaps": { "am": 30, "cr": 36 }   // 可省略：由 §21.3 自动推导
  },
  "rotation": [ /* §20 */ ],
  "effects": [ /* §18.3；音擎被动 / 4 件套 / 影画 / 潜能 / 队友（核心加成本身进 build.core） */ ],
  "cinema": [ /* §23.3 */ ],
  "assumptions": {
    "critMode": "expected",
    "onField": true,
    "stacks": { "ep-212": 2, "ep-214": 1 },
    "uptime": { "weapon.ep-2259.passive.fire_dmg": 1.0 },
    "rotationSeconds": 20,
    "sensitivity": {
      "stacks:ep-212": [1, 2, 3, 4],
      "event:anomaly.burn.count": [1, 2, 3]
    }
  },
  "sources": {
    "cinemaTextHash": "sha256:…",
    "skillTableHash": "sha256:…"
  },
  "validation": {
    "goldenFile": "golden.json"
  }
}
```

> `build.sets` 只允许两种：**4+2**（`set4` + `set2`）或 **2+2+2**
> （`set2` + `set2b` + `set2c`，`set4 = null`）。4+2+2 / 4+4 非法（6 个槽位装不下）；
> 详见 §28.5.2。
>
> `disc5.dmg_30` 是**元素限定**的属性伤害；`build.dmgElement` 必须等于角色属性
> （或由属性 2 件套显式给出），否则拒绝。面板的 `dmg` 行按该元素计，效果层不能
> 把它当 `all`——否则火伤会打到物理事件。

**字段规则**：

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| `schemaVersion` | 是 | 整数；引擎按版本分派，未知版本拒绝加载 |
| `engineVersion` | 是 | 语义化版本区间（如 `>=1.0 <2.0`）；超出拒绝加载 |
| `slug` / `agentId` | 是 | 必须与目录名、`agent-index.json`、`<slug>.json.meta.agentId` 三方一致 |
| `calculatorKind` | 是 | `personal` / `personal-only` / `stun` / `team`（预留）/ `hybrid`（预留） |
| `roleScope` | 是 | `dps` / `anomaly` / `stun` / `support` / `defense` / `special`；必须与预设一致 |
| `status` | 是 | `draft` / `partial` / `complete`；只有 `complete` 允许发布 |
| `damageModel` | 是 | `direct` / `anomaly` / `mixed` / `piercing` / `armorer`；决定默认路径与面板取行；`mixed` 表示直伤与异常事件并存，按事件各自的 `path` 结算 |
| `target` | 是 | 必须是已注册目标 id；本设计默认 `whiteboard-boss-60` |
| `baseline` | 是 | 相对值基准；本设计固定 `C0R1`，不要用「满精」当基准 |
| `build` | 是 | 固定配装；优化器只动副词条，不动音擎/影画/主词条（除非显式换方案）；`dmgElement` 必须与角色属性一致 |
| `rotation` | 是 | 至少 1 个事件；见 §20 |
| `effects` | 是 | 可以为空数组，但**空数组表示「确认没有局内效果」**，不是「还没填」 |
| `cinema` | 是 | 0~6；未建模的影画用 `status: "descriptive"` 显式标出 |
| `assumptions` | 是 | 层数、覆盖率、循环时长、`teamMode`；异常触发次数写进 `rotation[].count`，不在这里重复 |
| `sources` | 是 | `cinemaTextHash` / `skillTableHash`；用于检测源文本漂移 |
| `validation` | 否 | `goldenFile` 指向同目录的 `golden.json`；黄金值不在 `calculator.json` 内重复 |

### 19.4 加载与校验

加载流程（建议放在 `services/calculator_service.py`）：

```text
1. 扫描 strategy/*/calculator/calculator.json
2. 解析 schemaVersion → 结构校验（Pydantic）
3. 语义校验：
   - slug == 目录名
   - agentId 存在于 data/catalog/agents.json
   - agentId == <slug>.json 的 meta.agentId
   - damageModel 合法；target 已注册
   - rotation 事件 id 唯一、path 合法、倍率 > 0、count 为正整数
   - effects 的 target 在累加器白名单内
   - 每个 effect 的 status 已填；未建模的必须 not modeled
   - 影画等级 0~6；每个影画至少有一条记录（可以是 descriptive）
4. 构建：解析技能倍率 → 展开事件 → 合并效果 → 生成候选面板
5. 校验黄金值（可跳过，仅 CI）
```

**拒绝而不是回退**：档案缺失、字段未知、`agentId` 不匹配、效果 target 未知，
一律报错并指出文件与字段。不要「用默认值悄悄补上」——那会让报告看起来完整、
实际算的是别人的假设。

### 19.5 「互不兼容」的硬边界

| 边界 | 规则 |
| --- | --- |
| 档案 ↔ 代理人 | 1:1；`agentId` 必须匹配；不允许「通用档案」 |
| 档案 ↔ 档案 | 不继承、不合并、不共享 `rotation` / `effects` / `assumptions` |
| 档案 ↔ 引擎 | 引擎版本有 `engineVersion`；档案声明兼容区间；超出拒绝 |
| 档案 ↔ 目标 | 目标 id 显式；不允许隐式使用默认目标 |
| 档案 ↔ 报告 | `report.json` 的 `calculatorHash` 必须与当前 `calculator.json` 一致，否则标「已过期」 |

### 19.6 如果确实需要代码：窄接口插件

有些机制可能无法用数据表达（例如需要求解一个非线性方程）。此时允许：

```text
strategy/<slug>/calculator/custom.py
```

但必须满足：

- 只实现 `def build(ctx) -> list[Event]` 或 `def adjust(combat) -> combat`；
- **不得**重写乘区公式、面板公式、取整规则；
- 由 `calculator.json` 的 `"custom": "custom.py"` 显式声明；
- 只对该 `agentId` 加载；CI 必须跑该代理人的黄金值；
- 代码评审时按「新增机制」而不是「修公式」审。

**默认不要走这条路**。61 份代码是维护灾难；数据档案 + 共享引擎才是可持续的。

## 20. 理论循环（Rotation）与伤害事件

### 20.1 什么叫「理论循环」

本设计不模拟战斗过程，只定义一个**固定、可复现的伤害事件序列**：

- 技能顺序、次数、命中段数固定；
- 暴击按期望，不掷骰；
- 异常触发次数是**输入假设**，不是积蓄模拟；
- 循环时长固定，用于把总伤换算成「每循环」或「每秒」。

它的用途是**比较配装**，不是预测某次实战。报告必须带 `assumptions`，让读者知道
「这个 100% 是在什么循环下得到的」。

### 20.2 事件模型

```jsonc
{
  "id": "basic.caisheng.1",
  "label": "普通攻击：裁生 一段",
  "skill": "basic",
  "move": "普通攻击：裁生",
  "path": "normal",
  "scaling": "atk",
  "multiplier": 38.1,
  "hits": 1,
  "count": 1,
  "damageType": "fire",
  "tags": ["basic", "fire"],
  "critMode": "expected",
  "stunned": true
}
```

| 字段 | 说明 |
| --- | --- |
| `id` | 事件唯一 id；报告按它聚合 |
| `skill` | `basic` / `dodge` / `assist` / `special` / `chain` / `core` |
| `move` | 招式标题，必须能在 `<slug>.json` 的 `skills[].moves[].title` 中找到 |
| `path` | `normal` / `anomaly` / `piercing` / `armorer` / `turbulence` |
| `scaling` | `atk` / `def` / `hp` / `penforce` / `target_max_hp` |
| `multiplier` | **百分比数值**（38.1 表示 38.1%），加载时除以 100 |
| `hits` | 该事件的命中段数；多段可拆成多个事件，也可用 `hits` |
| `count` | 每循环触发次数 |
| `damageType` | 属性 / `all` / `anomaly` / `direct`；用于过滤增伤 |
| `tags` | 技能类型、攻击类型、机制标签；用于条件匹配 |
| `critMode` | `expected`（默认）/ `crit` / `non_crit` |
| `stunned` | 默认继承目标；白板固定 `true` |

> 最终结算次数 = `hits × count`。也可以把多段直接拆成多个事件；两种写法等价，
> 但不要既写 `hits=4` 又复制 4 个事件——那会重复乘。

异常事件用额外的 `anomaly` 块：

```jsonc
{
  "id": "anomaly.burn.1",
  "label": "灼烧触发",
  "path": "anomaly",
  "multiplier": 1.0,
  "count": 2,
  "anomaly": {
    "multiplier": 1250,
    "base": "fire"
  },
  "damageType": "anomaly",
  "tags": ["anomaly", "burn", "fire"]
}
```

> 异常事件的「次数」统一用 `count`，不要再用 `anomaly.triggers` 这样的第二套字段；
> 两层计数会让报告重复乘。

> **单位**：`multiplier` 与 `anomaly.multiplier` 在 JSON 里都写**百分数**，
> 加载时统一 `/100`。不要让一半事件写 0.381、另一半写 38.1——单位混用是这类
> 计算器最常见的 silent error。

### 20.3 技能倍率从哪来

`<slug>.json` 的 `skills[].moves[].growth[]` 已经有每个等级的倍率文本：

```text
level 16 / group 伤害倍率 / row "一段伤害倍率：38.1%\n二段伤害倍率：160.7%…"
```

建议写一个**解析器**（拟新增 tools/parse_skill_multipliers.py）：

1. 遍历 `skills[].moves[]`；
2. 取 `growth` 里 `group.name` 含「伤害倍率」的行；
3. 按换行拆段，按 `：` 取标签与数值，去掉 `%`；
4. 按 `level`（1–16）建表：`move.title → {level → {segment → value}}`；
5. 保留 `raw` 原文与 `<slug>.json` 的 sha256，供审计；
6. 找不到/重复/非数字 → 报错，不猜。

技能等级：

```text
skillLevel = 基础等级
           + 影画 C3/C5 的 +2（只加对应技能类别）
           + 核心技「技能等级 +1」（如果该角色有）
```

如果等级超过表的上限（当前抓取到 16），**不要外推**；标记
`status: "unsupported"`，并在报告里写明「该影画的技能 +2 未计入」。

### 20.4 异常 / 紊乱 / 异放的事件边界

| 类型 | 是否可作事件 | 需要的输入 | 本期 |
| --- | --- | --- | --- |
| 属性异常（灼烧/感电/碎冰/强击/侵蚀/风化） | 是 | 异常倍率、触发次数、异常精通、异常暴击 | ✅ 可做 |
| 紊乱 | 是 | 基底异常、已流逝时间 `t`、§6.1 的 450% + 时间项、紊乱增伤/暴击 | ⏳ 需要时间项 |
| 异放 | 是 | 原异常来源、触发者、异放倍率、异放增伤/暴击 | ⏳ 来源分离 |
| 乱流 | 是 | 基底异常、剩余时间 T、乱流倍率表 | ⏳ 时间项 |
| 耀变 | **否** | 独立队伍评分，不是伤害事件 | ❌ 不混进循环 |

本期建议先做「直伤 + 属性异常」；紊乱/异放/乱流按 §3.11–§3.13 的规格另开。
紊乱的**倍率表**已补在 §6.1，但引擎还没有接；不要用一个 `anomalyMultiplier` 糊过去。

### 20.6 循环的覆盖与自检

报告里必须写：

```jsonc
"coverage": {
  "events": 4,
  "damageShareCovered": 1.0,
  "unsupported": ["release", "disorder"]
}
```

自检规则：

- 事件的 `id` 唯一；`count` 为正整数；`multiplier > 0`（异常事件除外，允许 `1.0`）；
- 所有 `move` 都能在 `<slug>.json` 找到；找不到即报错；
- 事件伤害份额之和 ≈ 1（允许 <1 的缺口，但必须写明「未覆盖」）；
- 同一事件不得既算直伤又算异常；
- 循环时长 > 0；每秒伤害只在同一代理人内比较。

## 21. 词条最优分配算法

### 21.1 问题定义

给定：

- 固定的代理人、音擎（含精炼）、影画、核心、套装、4/5/6 主词条；
- 固定的白板目标与理论循环；
- 副词条预算 `N`（满配 54；非满配如 30）；

求一个整数分配 `n = (n_hp_flat, n_hp_pct, …, n_am)`，使总伤害最大：

```text
maximize   D(n) = Damage(panel(build, n), effects, rotation, target)
subject to Σ n_i = N
           0 ≤ n_i ≤ cap_i
           n 在 6 个驱动盘上可实际刷出（§21.4）
           n_i 为整数
```

其中 `n_i` 是**档数（roll）**，不是「几条副词条」。一条副词条 = 1 基础档 + 最多 5 次强化，
所以一条最多 6 档；一个盘 9 档（4 条基础 + 5 次强化）；6 个盘 54 档。
攻略页口语里的「54 条」也是这个意思，不要与「4 条副词条」混用。

### 21.2 为什么不能只按「总量 54」分配

如果只约束 `Σ n_i = 54` 和 `n_i ≤ 36`，优化器会给出类似
`AM 27 + ATK% 27` 的分配。它在数学上可行，在游戏里**刷不出来**：

- 一个盘只能有 4 条副词条，每条至少 1 档；
- 一个盘只有 9 档（4 基础 + 5 强化）；
- `AM 27 + ATK% 27` 需要每个盘平均 `AM 4.5 + ATK% 4.5 = 9 档`，
  这意味着另外两条副词条**一档都没有**——与「4 条、每条至少 1 档」矛盾。

> 这就是 §21.4 必须存在的理由。只做「单条上限 + 总量」的模型，会系统性地
> 高估满配伤害，并给出不可实现的「最优面板」。

### 21.3 单条上限 `cap_i`：按主词条排除盘位

`cap_i = 6 × (6 − excludedSlots_i)`。

`excludedSlots_i` 是「该副词条不能出现的盘位数」，来源：

| 盘位 | 固定/可选主词条 | 被排除的副词条 |
| --- | --- | --- |
| 1 号 | 固定生命 2200 | `hp_flat` |
| 2 号 | 固定攻击 316 | `atk_flat` |
| 3 号 | 固定防御 184 | `def_flat` |
| 4 号 | 攻击 30% / 生命 30% / 防御 48% / 暴击率 24% / 暴击伤害 48% / 异常精通 92 | 同名副词条 |
| 5 号 | 攻击 30% / 生命 30% / 防御 48% / 穿透率 24% / 增伤 30% | `atk_pct` / `hp_pct` / `def_pct`；穿透率与增伤**没有**同名副词条 |
| 6 号 | 攻击 30% / 生命 30% / 防御 48% / 冲击力 24% / 异常掌控 30% / 能量回复 60% | `atk_pct` / `hp_pct` / `def_pct`；冲击力/异常掌控/能量回复**没有**同名副词条 |

例子：

| 配装 | `cap_cr` | `cap_cd` | `cap_atk_flat` | `cap_hp_flat` |
| --- | ---: | ---: | ---: | ---: |
| 4 号暴击率 24% | **30**（5 盘 × 6） | 36 | 30 | 30 |
| 4 号暴击伤害 48% | 36 | **30** | 30 | 30 |
| 4 号异常精通 92 | 36 | 36 | 30 | 30 |
| 4 号攻击 30% + 5 号攻击 30% + 6 号攻击 30% | 36 | 36 | 30 | 30；`cap_atk_pct = 18`（3 盘 × 6） |

> 前端 `calculatorOptions.ts::calculateSubStatLimit()` 已经实现了这条规则
> （固定排除 1/2/3 + 4/5/6 主词条排除）；后端 `compare_service` 目前引用
> `options.MAIN_STAT_EXCLUDES` 但该名字不存在，是**现存阻断项**，见 §27.2。
> 本设计把「按盘位重算上限」收进后端单一真源，前端只做展示。

### 21.4 每盘可行性：4 条 × 9 档 × 单条 ≤ 6

把 6 个盘记为 `j = 1..6`，令 `x_ij` 为副词条 `i` 在盘 `j` 上的档数。可行解满足：

```text
x_ij ∈ {0} ∪ {1, 2, …, 6}        # 每个盘上每条最多 6 档（1 基础 + 5 强化）
Σ_i x_ij = 9                      # 每个盘 9 档
#{i : x_ij > 0} = 4               # 每个盘恰好 4 条副词条
x_ij = 0 若 i 是盘 j 的主词条      # 主副不重复
n_i = Σ_j x_ij
```

**必要但不充分**的条件（可以用来快速剪枝）：

```text
Σ n_i = 54
n_i ≤ cap_i
Σ_i ceil(n_i / 6) ≤ 24            # 每条至少占一个盘位，6 盘 × 4 条 = 24
```

**反例**：`cr = 36, cd = 18`。

- `Σ n = 54`、`cr ≤ 36`、`cd ≤ 36` 都满足；
- `Σ ceil = 6 + 3 = 9 ≤ 24` 也满足；
- 但 `cr = 36` 要求 6 个盘都放暴击率且每盘 6 档，此时每个盘只剩 3 档给另外 3 条；
  `cd = 18` 需要 3 个盘各 6 档，而每个盘最多再给 3 档 → 最多 9 档，不够。

**实用判定**：先用上面的必要条件剪枝，再对候选解跑一次最大流/构造：

1. 决定每条 `i` 占几个盘位 `d_i`：`ceil(n_i/6) ≤ d_i ≤ min(6 − excluded_i, n_i)`，
   且 `Σ d_i = 24`；
2. 二部图匹配：把 `d_i` 个「stat i 的盘位」分配到 6 个盘的 4 个槽位，
   排除主词条冲突；
3. 每个盘先给 4 条各 1 档（共 24 档），剩余 `54 − 24 = 30` 档是强化；
   对每个盘，把 5 档强化分给 4 条，单条最多 5 档；用一次流/贪心检查列和是否等于 `n_i`。

> 实现建议：不要在每个 beam 候选上跑完整流（太慢）；对**每个预算的 Top-K 候选**
> 跑一次，失败就丢弃并在报告里标 `infeasible`。优化器内部用必要条件剪枝，
> 输出前再做一次完整可行性检查。

### 21.5 目标函数 `D(n)`

`D(n)` 不是面板代理指标，而是**完整局内伤害**：

```text
D(n) = Σ_event damage(event, combat(panel(n), effects), target)
```

它必须复用 §18 的三层模型；不能用「攻击力 + 双爆 + 精通加权」之类的代理分。
原因：代理分与真实伤害的排序并不总是一致（暴击帽、穿透值下限、异常精通线性区、
属性增伤过滤都会改变排序）。

### 21.6 算法：两阶段束搜索 + 局部搜索

参考项目 `ZZZ-HP` 的做法（`ZZZ-HP:docs/guides/词条分析使用说明.md`）给了很好的骨架：

- 先按「加 1 档」的收益筛掉明显没有竞争力的词条；
- 每层只保留「累计提升 ≥ 本层最佳 × 比例」的分法；
- 用最小/最大保留路线兜底与截顶；
- 预算当刹车，花完就停；
- 对穿透这类「前期不值钱、终局很值钱」的词条开**专线**；
- 明确承认：「最优」= 给定参数与预算下搜索到的最好解，不是数学证明的最优。

本设计的落地版本：

```text
输入：N, build, target, rotation, effects
输出：allocation, panel, combat, damage, feasible, searchStats

0. 预筛（对应参考实现的「初始候选门槛 + 候选兜底」）
   在种子上算 v_i = D(n + e_i) − D(n)
   - 丢弃 v_i < threshold × max(v) 的词条（默认 threshold = 0，即只丢非正）；
   - 每组保留 top N 兜底（默认 4），防止「现在不值钱、终局值钱」的词条被误杀
     （典型：暴击伤害在暴击率帽之前、穿透在防御区拐点之前）；
   - 穿透专线不受预筛影响。
1. 种子
   a. 贪心：从空分配开始，每次加 1 档到当前边际最高的词条（重算，不缓存旧边际）
   b. 均衡：按 cap 比例分配
   c. 上一位形：从满配/非满配的已发布面板出发
   d. 穿透专线：先锁穿透率/穿透值到阈值，再分配其余
2. 粗搜（阶段 A，步长 3）
   对每个种子，按已用档数分层；每层扩展「给某词条 +3 档」；
   每层保留 Top B1（默认 64），按 D(n) 排序，去重（count vector 哈希）
3. 细搜（阶段 B，步长 1）
   取阶段 A 的 Top K（默认 8），从各自已用档数开始逐档 +1，直到 N；
   每层保留 Top B2（默认 256）；
   每层用必要条件剪枝（Σ、cap、ceil）
4. 局部搜索
   对阶段 B 的 Top K：
   - 1-swap：从 i 移 1 档到 j，若 D 提升则接受，直到无提升；
   - 2-swap：对 Top 3 再做一次成对交换；
   - 每次移动后检查可行性与 cap
5. 输出
   取 D 最大的可行解；同分按 allocation 字典序（保证确定性）
```

伪代码：

```python
def optimize(n_budget, build, target, rotation):
    seeds = [greedy_seed(), balanced_seed(), previous_seed(), pen_seed()]
    candidates = []
    for seed in seeds:
        beam = [seed]
        for used in range(seed.total, n_budget + 1, 3):
            beam = top_b(expand(beam, step=3), b=64)
        candidates.extend(beam[:8])
    beam = candidates
    for used in range(max(c.total for c in beam), n_budget + 1):
        beam = top_b(expand(beam, step=1), b=256)
    best = None
    for state in beam[:8]:
        state = local_search(state, swaps=2)
        if feasible(state) and (best is None or state.damage > best.damage):
            best = state
    return best
```

> 粗搜的步长 3 只用于缩小搜索范围；若 `N` 不是 3 的倍数，余数在细搜补。
> 伪代码省略了「每一步不得超过 `N`」的边界检查与不可行候选的丢弃。

### 21.7 复杂度与缓存

- 每层除了 top-B，还可以按「累计提升 ≥ 本层最佳 × 比例」再筛一道，并用
  min/max 保留路线兜底；top-B 是它的等价实现，本设计把 `beamWidth` 与
  `retentionRatio` 都记进 `searchStats`，便于复现；
- 评估次数 / 时间上限是**刹车**：打满就停，输出当时最好的可行解，并在
  `search.budgetHit = true` 里标明「不是自然跑完」；
- 一次评估 = 面板 + 局内效果 + 事件结算；本项目的 Python 实现预计 **0.5–2 ms/次**；
- 54 档 × 10 词条 × 256 宽度 ≈ **13.8 万次**评估 → 约 **2–5 分钟/代理人**（单核）；
- 61 个代理人 × 5 个预算档 ≈ 10–25 小时；离线批处理可接受，必要时并行；
- 缓存键：`(agentId, weaponId, refinement, cinema, mainStats, sets, tuple(n))`；
- 面板缓存与伤害缓存分开：同一面板可复用于多个事件；
- 不要缓存「边际值」跨层复用——边际随当前分配变化，缓存会引入偏差。

### 21.8 输出格式

```jsonc
{

  "panel": { "atk": 2538.1, "am": 510, "ac": 255.4, "cr": 5, "cd": 50, "dmg": 30, "pr": 0, "pv": 54 },
  "combat": { "atk": 2538.1, "am": 600, "dmg": 70, "cr": 5, "cd": 50 },
  "damage": {
    "total": 60713.49,
    "byPath": { "normal": 0, "anomaly": 60713.49 },
    "byEvent": [{ "id": "anomaly.burn", "damage": 60713.49 }]
  },
  "feasible": true,
  "infeasibleReason": null,
  "search": {
    "algorithm": "two-stage-beam+local",
    "evaluations": 138240,

    "seeds": ["greedy", "balanced", "previous"],
    "deterministic": true
  },
  "warnings": []

```

### 21.9 验证：必须有独立 oracle

| 验证 | 方法 | 通过标准 |
| --- | --- | --- |
| 小预算穷举 | `N ≤ 12` 时枚举所有 composition，逐条算 `D(n)` | beam 结果 = 穷举最优（同分同 allocation） |
| 可行性 | 对输出跑 §21.4 的流/构造 | 100% 可行 |
| 单调性 | `D(N+1) ≥ D(N)`（重新优化后） | 不下降；允许相等（帽/阈值） |
| 与贪心对比 | beam vs greedy | beam ≥ greedy |
| 稳定性 | 固定输入跑两次 | 字节级一致（除时间戳） |
| 与参考实现对比 | 同一简单直伤角色、同一目标 | 差异 < 2%，且差异有解释 |

> 不要用「beam 自己和自己比」当验证；必须有**独立实现**的 oracle（穷举或朴素贪心）。
> 这是本项目 `damage-formulas.md` 契约 C1–C36 的同一条纪律。

### 21.10 为什么不用梯度 / 动态规划

- `D(n)` 对 `n_i` 是**离散、非光滑**的：暴击率帽、穿透值下限、异常精通线性区、
  属性增伤过滤都会造成折点；
- 状态空间是 10 维 composition，`C(54+9,9) ≈ 1.2×10^10`，DP 需要把 10 维压成
  可枚举的前缀，代价不低于 beam；
- beam 的误差是**可度量**的（小预算穷举对照），而梯度的误差在折点附近不可控。

## 22. 驱动盘评分与副词条有效性

### 22.1 先定义「有效」

对当前配装 `n`，副词条 `i` 的**单档边际价值**：

```text
w_i(n) = D(n + e_i) − D(n)
```

即「多给 1 档 `i`，总伤害增加多少」。它必须用**完整局内伤害**算，不能用面板代理分。
若 `n_i` 已达 `cap_i`（主词条排除盘位后的上限），该方向的 `w_i` 记为 **0**（不可再加），
不是负值、也不是「换一条」的收益。

| 判定 | 条件 | 含义 |
| --- | --- | --- |
| `dead` | `w_i = 0` | 对该配装完全无效（生命/防御对攻击角色、暴击率对纯异常、穿透值超过防御下限…） |
| `low` | `0 < w_i < 0.1 × w_max` | 有效但很低，通常只值 1–2 档 |
| `effective` | `0.1 × w_max ≤ w_i < 0.5 × w_max` | 正常有效词条 |
| `core` | `w_i ≥ 0.5 × w_max` | 核心词条，优先堆 |

> `w_i` 是**局部**的：同一词条在 30 条与 54 条时价值不同；在暴击率 90% 与 100% 时
> 也不同。所以「这个词条对这个角色有没有效」必须带**当前配装**回答，不能给一个
> 永久不变的静态表。

### 22.2 单盘评分公式

一个满级盘有 4 条副词条、9 档，单条最多 6 档。把该盘上词条 `i` 的档数记为 `r_i`：

```text
S_disc = 100 × Σ_i (r_i × w_i) / (6 × w_(1) + w_(2) + w_(3) + w_(4))
```

- `w_(1) ≥ w_(2) ≥ w_(3) ≥ w_(4)` 是当前配装下**价值最高的 4 个词条**；
- 分母是「理论完美盘」：最好的词条 6 档，另外三条各 1 档（共 9 档）；
- 分子是该盘实际 9 档的加权和；
- 结果上限 100；允许超过 100 的浮点误差，展示时 `min(100, S)`。

> 若有效词条不足 4 个，`w_(3)` / `w_(4)` 记 0；此时「6 档核心 + 3 档次核心」的盘会超过
> 100，按 100 截顶。分母是**可解释的满分基准**，不是严格数学最大值。

> **为什么不把分母写成 `9 × w_max`**：单个盘里同一条词条最多 6 档，剩下 3 档必须
> 分给另外 3 条；用 `9 × w_max` 会让「6 档核心 + 3 档垃圾」只有 66 分，
> 而事实上它已经是该盘能做到的最好集中度。分母用 `6w1 + w2 + w3 + w4` 才对齐
> 「4 条 × 9 档」的真实上限。

### 22.3 主词条评分

主词条不参与上面的副词条分，单独给：

```text
S_main = 100 × (main_value_in_rolls × w_main) / (10 × w_(1))
```

主词条通常相当于 **10 档**该词条，所以分母用 `10 × w_(1)`：满分主词条（10 档都是
当前最有价值词条）= 100；如果主词条的价值只有最好词条的一半，就是 50。

`main_value_in_rolls` 是主词条相当于多少档该词条：

| 主词条 | 数值 | 单档 | 折算档数 |
| --- | ---: | ---: | ---: |
| 暴击率 | 24% | 2.4% | 10 |
| 暴击伤害 | 48% | 4.8% | 10 |
| 攻击力% | 30% | 3% | 10 |
| 生命值% | 30% | 3% | 10 |
| 防御力% | 48% | 4.8% | 10 |
| 异常精通 | 92 | 9 | 10.22 |

主词条分只用于「同槽位换主词条」的比较；跨槽位（4 号 vs 5 号）不能直接比。

### 22.4 示例：菲欧妮的 54 条面板

用 §23 的示例口径（纯异常、54 条攻略面板、涅槃 R1），单档价值：

| 词条 | `w_i`（相对总伤） | 判定 |
| --- | ---: | --- |
| 攻击力% | **1.873%** | core |
| 异常精通 | **1.500%** | core |
| 攻击力（小攻击） | 0.749% | effective |
| 穿透值 | 0.535% | effective |
| 暴击率 | 0 | dead（异常不吃常规暴击） |
| 暴击伤害 | 0 | dead |
| 生命值 / 生命值% / 防御力 / 防御力% | 0 | dead |

> 这组数直接解释了：为什么菲欧妮的攻略副词条优先级是
> 「异常精通 > 攻击力% > 攻击力 > 穿透值」，双爆不在链上。

单盘评分例子：

| 盘 | 副词条 | 分子 | 评分 |
| --- | --- | ---: | ---: |
| A | 异常精通 ×6、攻击力% ×1、攻击力 ×1、穿透值 ×1 | `6×1.5 + 1.873 + 0.749 + 0.535 = 12.157` | **86.7** |
| B | 暴击率 ×6、暴击伤害 ×1、生命值 ×1、防御力 ×1 | `0` | **0** |
| C | 攻击力% ×4、异常精通 ×4、攻击力 ×1 | `4×1.873 + 4×1.5 + 0.749 = 14.241` | **100（截顶）** |

- 盘 A 是「毕业盘」：核心词条集中，但没有浪费档数；
- 盘 B 是「双爆分很高」但对该角色**完全无效**的典型；
- 盘 C 的 4+4+1 只占 3 条词条、却用满 9 档；真实盘必须第 4 条至少 1 档（总共 10 档），
  所以这个组合**不可行**，分数截顶到 100 只用于说明公式上限，不能当成可用盘。

### 22.5 评分的使用边界

| 用法 | 是否成立 | 说明 |
| --- | --- | --- |
| 同一角色、同一配装下比较两个盘 | ✅ | `w_i` 固定，分数可比 |
| 同一角色、不同配装比较 | ⚠️ | `w_i` 会变；要用同一锚点面板重算 |
| 跨角色比较盘 | ❌ | `w_i` 完全不同；「双爆分」这类通用分没有意义 |
| 用评分替代伤害计算 | ❌ | 评分是解释工具，最终排序用 `D(n)` |
| 把「重要副词条」当评分权重 | ❌ | `zzz_calculator` 的 `importantSubStats` 只做高亮，不进计算；本设计同此 |

> 评分的目标是**让人看懂**「这个盘为什么好/坏」，不是替代优化器。
> 真正的取舍仍然走 §21 的 `D(n)`。

## 23. 影画 / 音擎相对值

### 23.1 基准与记法

本设计统一用：

```text
C0R1 = 0 影画 + 专武精炼 1
```

- `C0R1` 的总伤害记为 **100.00%**；
- `C2R1` = 2 影画 + 专武 R1；
- `C0 + 双生 R5` = 0 影画 + 双生泣星精炼 5；
- 不使用含糊的「00 / 01」——不同社区对「00」的定义不一致（0 影 0 精 / 0 影无专武），
  文档里必须写全。

基准的固定条件：

- 白板目标 `whiteboard-boss-60`（§17）；
- 同一套 4/5/6 主词条、同一套套装、同一套核心；
- **54 条满配**；默认按 §21 重新优化（`optimalPanel`），同时给出同面板（`samePanel`）；
- 同一理论循环、同一暴击期望、同一异常触发假设。

### 23.2 同面板 vs 各自最优面板

| 模式 | 做法 | 回答的问题 | 用途 |
| --- | --- | --- | --- |
| `samePanel` | 固定基准的 54 条分配，只换影画/音擎 | 「这个物品本身值多少」 | 解释机制、隔离变量 |
| `optimalPanel` | 每个变体重新跑 §21 优化 | 「实际养成后值多少」 | **标题数字**、抽取建议 |

两者都要出。只给 `samePanel` 会低估「换音擎后副词条要重排」的收益；
只给 `optimalPanel` 会把「副词条重排」的收益算到音擎头上，读者看不出原因。

### 23.3 影画的结构化建模

影画不是「一条增伤」。它至少有三类：

| 类型 | 例子 | 建模方式 |
| --- | --- | --- |
| 纯数值 | C2「对灼蚀敌人伤害 +30%」 | `modifiers`：`dmg +30`，条件 `enemy_under_state(state=zhuoshi)` |
| 技能等级 | C3/C5「技能等级 +2」 | `skillLevelBonus`：`basic/special/... += 2`，重算倍率 |
| 改变循环 | C4「额外触发一次 600% 异放」 | `rotationPatches`：新增/修改事件，不是乘区 |
| 机制解锁 | C1「升变 +1」、C6「无视 15% 抗性」 | `modifiers` + `rotationPatches` + `notes`；不能只用一条增伤 |

```jsonc
{
  "level": 2,
  "name": "好奇心害不死猫",
  "status": "modeled",
  "modifiers": [
    {
      "target": "dmg",
      "kind": "pct",
      "value": 30,
      "damageType": "all",
      "phase": "in_combat",
      "readout": "per_path",
      "condition": { "kind": "enemy_under_state", "state": "zhuoshi" },
      "uptime": 1.0,
      "notes": "灼烧持续时间 +2 秒；这里只建模 +30% 增伤，持续时间对触发次数的影响见 rotationPatches。"
    }
  ],
  "rotationPatches": [
    { "op": "set", "event": "anomaly.burn", "field": "count", "value": 3 }
  ],
  "skillLevelBonus": {},
  "notes": "示例按 100% 灼蚀覆盖。"
}
```

**影画状态**必须逐条标：

| `status` | 含义 | 报告里怎么显示 |
| --- | --- | --- |
| `modeled` | 数值/条件/覆盖率都已建模 | 给出相对值 |
| `partial` | 只建模了一部分（如只算抗性、没算异放防御） | 给出相对值 + `partial` 标记 |
| `descriptive` | 只登记文本，未建模 | 不给相对值，写「未计入」 |
| `not_applicable` | 该影画对伤害无影响（纯功能） | 不给相对值，写「无伤害影响」 |

> **绝不允许把未建模的影画当 0 混进排名。** 那会让「6 影」看起来只提升一点，
> 而实际有一半机制没算。报告必须把 `descriptive` 的影画单列。

### 23.4 音擎精炼的结构化建模

音擎的 `[局内生效]` 特效必须从「武器库」里单独建模，并且**逐精炼查数组**。
以涅槃初翎为例（Wiki 原文）：

```jsonc
{
  "id": "ep-2259",
  "name": "涅槃初翎",
  "grade": "S",
  "base": { "kind": "atk", "value": 713 },
  "substat": { "label": "异常掌控", "value": 30, "kind": "pct", "to": "ac_pct" },
  "effect": {
    "name": "破壳日",
    "tag": "异常",
    "raw": "装备者的异常精通提升90/99/108/117/126点；队伍中任意角色对敌人造成的属性异常伤害产生暴击时，装备者造成的火属性伤害提升40%/44%/48%/52%/56%，持续20秒，重复触发刷新持续时间。",
    "targets": [
      {
        "target": "am", "kind": "flat",
        "perRefinement": [90, 99, 108, 117, 126],
        "phase": "in_combat", "readout": "per_path", "status": "modeled"
      },
      {
        "target": "dmg", "kind": "pct", "damageType": "fire",
        "perRefinement": [40, 44, 48, 52, 56],
        "phase": "in_combat", "readout": "per_path",
        "condition": "any_ally_anomaly_crit", "duration": 20, "refresh": true,
        "status": "modeled"
      }
    ]
  }
}
```

要点：

- **`base` / `substat` 是局外面板**，`effect` 是**局内修正**；两者不能混。
- `perRefinement` 长度 5；`R1` 取 `[0]`。不要写 `base + step × (r-1)`，
  因为精炼阶梯不保证线性。
- `damageType: "fire"`：只对火属性事件生效；不要让火伤加成打到物理/以太事件。
- `condition`：条件不满足时效果为 0，但 `status` 仍是 `modeled`（条件本身是建模的一部分）。
- `readout: "per_path"`：直伤在命中时读、异常在积蓄时读；只有明确只进一侧时才写
  `snapshot` / `realtime`。**不要给一个全局 `readout` 然后所有路径共用**。

**条件不满足的真实例子**：壳中之灵（`ep-1883`）的文本是

> 装备者的异常精通提升 90/103/117/130/144 点；**以太属性**的装备者进入前场或发动
> [特殊技]/[强化特殊技] 时获得增益效果：对处于属性异常状态下的敌人造成的伤害提升
> 20%/23%/26%/29%/32%，触发的所有属性异常伤害和[紊乱]伤害提升 10%/11.5%/13%/14.5%/16%。

菲欧妮是**火属性**，所以：

- 异常精通 +90 起，**生效**；
- 「以太属性的装备者」那一段，**条件不满足**，不生效；
- 攻略里写「相比专武只少了 40% 增伤」，指的就是这个——不是武器坏了，是条件不匹配。

### 23.6 菲欧妮示例：01 = 100%，满精双生 = 83%

**示例口径**（必须随报告一起展示，否则数字不可复现）：

- 白板目标 `whiteboard-boss-60`；
- 54 条攻略面板：`AM 30 / ATK% 11 / ATK 6 / PEN 6 / HP% 1`；
- 主词条：4 号异常精通 92、5 号火伤 30%、6 号异常掌控 30%；
- 套装：4 自由蓝调 + 2 法厄同之歌（只计 2 件套面板；4 件套局内效果未计）；
- **纯异常路径**（示例为了对齐「满精双生 ≈ 83%」；正式报告用 `mixed` 循环，直伤事件另计，数值会略有不同）；
- 未计队友；
- 涅槃初翎被动按 100% 覆盖；双生按 2 层；嵌合按 1 层（另给 3 层）；
- `C0R1 = 100.00%`。

> 「涅槃被动 100% 覆盖」等价于 `any_ally_anomaly_crit` 恒真：要么队伍里有异常暴击，
> 要么自身能触发。若按 `teamMode: solo` 且自身没有异常暴击，该条件为假，
> 40% 火伤不生效，上表数字会下降。报告必须把这条写进 `assumptions`。

> 用户口语里的「01 菲欧妮」= **0 影画 + 专武精炼 1**，对应本表的 `C0R1`；
> 「00 菲欧妮 + 满精双生」= **0 影画 + 非专武**（双生 R5），对应 `C0 + 双生 R5`。
> 武器精炼没有 0 档，所谓「00」只是「不带专武」，不是「专武 0 精炼」。

| 变体 | 同面板相对值 | 说明 |
| --- | ---: | --- |
| 涅槃初翎 R1 | **100.00%** | 基准 `C0R1` |
| 涅槃初翎 R2 | 103.89% | AM 99 / 火伤 44 |
| 涅槃初翎 R3 | 107.85% | |
| 涅槃初翎 R4 | 111.88% | |
| 涅槃初翎 R5 | **115.98%** | 满精 |
| 双生泣星 R5 ×1 层 | 76.95% | |
| 双生泣星 R5 ×2 层 | **83.57%** | **与「满精双生约 83%」吻合** |
| 双生泣星 R5 ×3 层 | 90.19% | |
| 双生泣星 R5 ×4 层 | 96.81% | 满层接近专武 |
| 壳中之灵 R5（仅精通） | 83.35% | 以太条件不满足，只吃 AM |
| 嵌合编译器 R1 ×1 层 | 86.95% | |
| 嵌合编译器 R5 ×1 层 | 100.77% | |
| 嵌合编译器 R5 ×3 层 | **118.76%** | 3 层满 |

**结论怎么读**：

- 「满精双生 00 菲欧妮 ≈ 83%」在**2 层**假设下成立（83.57%）；
  如果按 4 层满层，它是 96.81%，不是 83%——**层数假设必须写进攻略**；
- 嵌合编译器 R5 在 3 层时反超专武 R1（118.76%），但它的前提是
  「特殊技/强化特殊技」持续叠层：R5 1 层只有 100.77%，R1 1 层只有 86.95%。
  这类「高层数才强」的音擎不能只给一个满层数字；
- 壳中之灵看起来与双生 2 层接近（83.35% vs 83.57%），但它是**只吃 AM** 的结果；
  换成以太角色，第二段生效，排名会变。

> 这些数字是**示例口径**，不是最终攻略结论。正式报告由
> `strategy/<slug>/calculator/report.json` 生成，必须带 `assumptions` 与 `status`。
> 与现状对比：旧口径生成的 `data/reports/build-compare.json` 里菲欧妮的音擎排序是
> 「嵌合 113.9% > 双生 108.2% > 涅槃 100%」——因为它**没建模专武被动**，
> 把涅槃的 AM 90 + 火伤 40% 全丢了。这正是 §18 要补的洞。

### 23.7 影画示例：C2 / C6 能算，C1/C3/C4/C5 先标未建模

同一示例口径下：

| 影画 | 效果 | 状态 | 同面板相对值 |
| --- | --- | --- | ---: |
| C0 | 基准 | `modeled` | 100.00% |
| C1 | 灼蚀敌人异常暴伤 +25% | `descriptive`（缺异常暴击率来源） | — |
| C2 | 对灼蚀敌人伤害 +30% | `modeled`（100% 覆盖） | **117.65%** |
| C3 | 技能等级 +2 | `partial`（倍率表到 16 级，不外推） | — |
| C4 | 额外异放 600% | `descriptive`（缺异放段数/倍率） | — |
| C5 | 技能等级 +2 | `partial` | — |
| C6 | 无视 15% 全属性抗性；异放无视 40% 防御 | `partial`（抗性已算；异放防御未算） | **115.00%** |
| C2 + C6 | 组合 | `partial` | **135.29%** |

- C2 的 117.65% = `(1 + 0.70 + 0.30) / (1 + 0.70)`，即增伤区从 1.7 到 2.0
  （按「造成的伤害提升」进增伤区**加算**；若官方实际是独立乘区，应为 130%，届时改 `target`）；
- C6 的 115.00% = 白板抗性区从 1.0 到 1.15；
- C6 的「异放无视 40% 防御」没有计入；若异放占比 20%，它还会再带来约 2–3 个百分点；
- C1/C3/C4/C5 不给数字，不是「0 提升」，而是「还没建模」。报告里必须这样写。

## 24. 非满配 vs 满配：边际收益

### 24.1 三个定义

| 符号 | 定义 | 回答 |
| --- | --- | --- |
| `D(N)` | 预算 `N` 档、**重新优化**后的最高伤害 | 「N 条能做到多少」 |
| `G(N)` | `D(54) / D(N) − 1` | 「离满配还差多少」 |
| `m(N)` | `D(N) − D(N−1)` | 「第 N 条值多少」 |
| `A(N)` | `G(N) / (54 − N)` | 「剩下每条平均要补多少差距」 |

### 24.2 三条曲线，不能混

| 曲线 | 做法 | 用途 |
| --- | --- | --- |
| `optimal` | 每个 `N` 都跑 §21 的优化器 | **权威**：非满配的最优面板 |
| `drop` | 从满配出发，每次去掉当前边际最低的 1 档 | 便宜；回答「如果只是拆条会怎样」 |
| `actual` | 用户实际面板在同一个 `N` 下的伤害 | 回答「我现在这套比最优差多少」 |

> `actual` 必须与 `optimal` **同武器 / 同套装 / 同主词条**；不同 build 只能标
> `crossBuild`，不能说「差多少」——那不是词条分配差异，是整套配装差异。

只给 `drop` 会低估非满配的潜力（因为不重排）；只给 `actual` 会无法区分
「词条少」与「词条配错」。报告建议三条都给，至少给 `optimal` + `actual`。

### 24.3 菲欧妮示例：54 → 30 的差距

同一示例口径（纯异常、涅槃 R1、54 条攻略面板为满配锚点）：

| `N` | 示例分配（`drop` 曲线） | 相对满配 | 离满配差距 `G` | 平均每条 `A` |
| ---: | --- | ---: | ---: | ---: |
| 54 | AM 30 / ATK% 11 / ATK 6 / PEN 6 / HP% 1 | 100.00% | 0.00% | — |
| 45 | AM 30 / ATK% 11 / ATK 4 | 95.46% | 4.76% | 0.53% |
| 40 | AM 29 / ATK% 11 | 91.17% | 9.69% | 0.69% |
| 35 | AM 24 / ATK% 11 | 84.23% | 18.73% | 0.99% |
| 30 | AM 19 / ATK% 11 | 77.28% | 29.39% | 1.22% |
| 25 | AM 14 / ATK% 11 | 70.34% | 42.16% | 1.45% |
| 20 | AM 12 / ATK% 8 | 63.59% | 57.26% | 1.68% |

对照：攻略页现有的 30 条非满配面板（`AM 21 / ATK% 8 / ATK 1`）是 **75.98%**，
离满配 **31.61%**；比上面的 `drop` 30 条（77.28%）低 **1.30 个百分点**。
这说明：

- 非满配不是「满配按比例缩小」；同样 30 条，分配不同，差 1–2 个百分点；
- 30 条时仍然应该把档数集中到 AM / ATK%，而不是平均撒；
- 攻略页的「非满配毕业面板」可以用优化器复核，而不是手调。

> 这里用的是 `drop` 曲线，不是 `optimal`。`optimal` 需要每个 N 跑一次 §21，
> 预计比 `drop` 高 0–2 个百分点；正式报告以 `optimal` 为准。

### 24.4 单条边际随预算变化

| 词条 | 满配 54 时 +1 档 | 30 条时 +1 档 |
| --- | ---: | ---: |
| 攻击力% | +1.873% | +1.962% |
| 异常精通 | +1.500% | +1.796% |
| 攻击力（小攻击） | +0.749% | +0.784% |
| 穿透值 | +0.535% | +0.518% |
| 暴击率 / 暴击伤害 | 0 | 0 |
| 生命值 / 防御力 | 0 | 0 |

读法：

- 菲欧妮的优先级在 30 与 54 都是「ATK% ≈ AM > ATK > PEN」，双爆/生存为 0；
- 但这不意味着所有角色都稳定：暴击率接近 100% 时，`w_cr` 会掉到 0；
  穿透值把有效防御打到 0 后，`w_pen` 也会掉到 0；
- 因此**每个预算都要重算边际**，不能拿满配的表去指导 30 条。

### 24.5 断点与非线性

边际曲线会在这些位置跳变：

| 断点 | 现象 | 处理 |
| --- | --- | --- |
| 暴击率 100% | 再加暴击率的 `w_cr` 从正变 0（常规）；锋御上限 200% | 在优化器里用 `min(cr, cap)`，不要线性外推 |
| 有效防御 0 | 再加穿透值/穿透率的 `w_pen` 变 0 | 防御区 clamp 到 1；边际用有限差分 |
| 异常精通上限 | `AM/100` clamp 到 10（1000 精通） | 高精通配装会看到平台 |
| 增伤区上限 | `1 + Σdmg` clamp 到 6 | 极端叠增伤会平台 |
| 影画/音擎阈值 | 例如「异常精通超过 120 点」才触发 | 在 `condition` 里显式建模，不能当连续收益 |

> 这也是为什么 §21 用离散搜索而不是梯度：这些断点正好落在最优解附近。

## 26. 数据管线改造

### 26.1 音擎效果：从 `multi_table` 到 `effect`

现状：`refresh_weapon_presets.py` 的 `tables_text()` 已经把音擎页的
`multi_table` 拼成文本，但 `parse()` 只提取「初始/满级面板」，效果文本被丢掉。

改造步骤：

1. 在 `parse()` 里保留 `effect_text`：取 `multi_table` 中包含「音擎效果」表头的那一行，
   去掉 HTML，按段落拆；
2. 解析面板之后的第一段为**效果名**（如「破壳日」）；
3. 用正则提取数字数组：
   ```text
   90/99/108/117/126
   40%/44%/48%/52%/56%
   ```
4. **不要自动猜目标**。先写入：
   ```jsonc
   "effect": {
     "name": "破壳日",
     "tag": "异常",
     "raw": "…",
     "targets": [],
     "status": "descriptive"
   }
   ```
5. 人工（或带评审的脚本）把 `targets` 补成 `perRefinement` 数组与 `condition`；
   补完后 `status: "modeled"`。

> 自动猜「哪个数字对应异常精通、哪个对应火伤」在文本顺序变化时会静默出错。
> 宁可先 `descriptive`，也不要猜错后让报告看起来完整。

### 26.2 影画：手工结构化 + 文本哈希

影画文本在 `<slug>.json` 的 `cinemas[]`，但自动解析不可靠（条件、次数、目标都可能变）。
建议：

- 在 `calculator.json` 的 `cinema[]` 里逐级维护；
- 每条记录带 `sourceTextHash`（`<slug>.json` 对应影画文本的 sha256）；
- 构建时比对：哈希变了 → 报告标「影画文本已更新，需复核」，**不要自动沿用旧建模**；
- `cinemaPriority.keyLevels` 仍是编辑推荐，不参与计算。

### 26.3 技能倍率：构建期解析，不新增全局数据集

`<slug>.json` 已经含 1–16 级倍率文本。建议：

- 拟新增 tools/parse_skill_multipliers.py，输出
  `strategy/<slug>/calculator/multipliers.json`（生成物，带 `sourceSha256`）；
- 或直接在 `build_agent_calculator.py` 里解析，把结果嵌进 `report.json` 的
  `multiplierSource`，不落独立文件；
- 二选一，不要同时维护两份。推荐**前者**：报告可复算，`--check` 能检测漂移。

解析规则：

| 文本 | 解析 |
| --- | --- |
| `一段伤害倍率：38.1%` | `segment="一段"`, `value=38.1` |
| `伤害倍率：1294.3%` | `segment="", value=1294.3` |
| `异放倍率：525%` | 存到 `release` 组，不混进 `damage` |
| `能量消耗：40点` | 忽略（不是倍率） |
| `失衡倍率：…` | 存到 `stagger` 组，不混进 `damage` |

### 26.4 4 件套与队友

- `drive-discs.json` 已有 `setEffect4` 文本；新增 `effect4` 结构化映射
  （与 `effect2` 同一模式），未映射的标 `null` + `effect4Note`；
- 4 件套效果多是条件触发（例如「强化特殊技命中后，属性异常积蓄抗性 −20%」），
  必须按 `Effect` 建模，不能当常驻面板；
- 队友 Buff 本期不做；如果要做，沿用参考实现的**冻结快照**：外部来源用
  `{角色, 配置哈希, 捕获时间, 面板, 修正参数}`，优化期间固定，刷新才更新；
  不得实现「A+B 联合驱动盘搜索」。

```jsonc

    "agentId": "ep-2145",
```

### 28.1 术语、单位与取整

| 术语 | 定义 | 备注 |
| --- | --- | --- |
| **档（roll）** | 一次副词条强化单位 | 一条副词条 = 1 基础档 + 最多 5 次强化 = 最多 6 档 |
| **条** | 口语里的「54 条」= 54 档总量 | 不是「4 条副词条」；一个盘 9 档 = 4 基础 + 5 强化 |
| **hits** | 一次事件内的命中段数 | 最终结算次数 = `hits × count` |
| **count** | 一次循环内该事件触发次数 | 不要再用 `triggers` 之类的第二套计数字段 |
| **t** | 基底异常**已流逝**时间（秒） | 用于 §6.1 紊乱倍率 |
| **T** | 基底异常**剩余**时间（秒），`T = 有效持续时间 − t` | 用于 §12 乱流倍率 |
| **C0R1** | 0 影画 + 专武精炼 1 | 相对值基准，固定 100.00% |
| **绝对伤害** | 乘上目标常数 `K`、技能倍率、事件次数后的伤害 | 只在同一代理人内可比 |
| **相对值** | `D(variant) / D(C0R1)` | 百分比，保留 2 位小数 |

**单位与取整**：

- JSON 里的所有百分比写**数值**（`38.1` 表示 38.1%），加载时统一 `/100`，**只除一次**。
- 优化目标 `D(n)` 与中间量用 **float**，不取整、不四舍五入；只在**展示**时取整。
- 报告相对值保留 **2 位小数**；绝对伤害展示取整；游戏内「向上取整」只用于显示，
  **不得**进入优化目标（逐段取整会改变排序）。
- 任何「取整」必须写明是 `floor` / `trunc` / `round`；本设计的异常掌控用 `floor`，
  伤害等级区用 `trunc(…, 4)`。

### 28.2 目标与读数：补齐字段与优先级

`TargetPreset` 增加三个字段（当前缺失）：

| 字段 | 类型 | 默认 | 语义 |
| --- | --- | --- | --- |
| `fixed_defense` | float | 0 | 初始固定防御，进入 `(基础防御 × (1 + 初始防御%) + 固定防御)` 的加法侧 |
| `distance_falloff` | float | 1.0 | 目标默认距离衰减；`RealtimeReadings.distance_falloff` 可逐事件覆盖 |
| `stunned_default` | bool | true | 事件未写 `stunned` 时的默认值 |

**优先级（必须写死）**：

```text
事件.stunned             > target.stunned_default
RealtimeReadings.distance_falloff > target.distance_falloff
target.attribute_resistance 是「该事件属性」的抗性，不是全局抗性
target.fixed_defense 进入 `(基础防御 × (1 + 初始防御%) + 固定防御)` 的加法侧，不进入穿透侧
```

> v1 的 `初始防御%` 恒为 0（白板无防御加成）；未来要加时，`target_defense()` 需同时
> 增加 `initial_defense_pct` 参数，不能把固定防御直接加到 `base_defense` 上。

> 当前 `TargetParams.fixed_defense` 字段存在但 `target_defense()` 没有使用；
> 实现时必须补进去，或在白板目标上断言 `fixed_defense == 0`。本设计选择**补进去**，
> 因为公式 §3.4 明确有「初始固定防御」。

**读数归属（逐项写死）**：

| 读数 | 直伤 | 异常 | 来源 |
| --- | --- | --- | --- |
| 攻击力 / 增伤 / 异常精通 / 穿透率 / 穿透值 / 等级 | 命中实时 | **积蓄时快照** | §4.2 |
| 暴击率 / 暴击伤害 | 命中实时 | **不参与**（异常用自己的暴击） | §3.3 |
| 抗性 / 抗性降低 / 防御降低 / 无视防御 / 无视抗性 | 实时 | 实时 | §4.2 |
| 失衡易伤 / 异常增伤 / 异常暴击 | 实时 | 实时 | §4.2 |
| 距离衰减 | 实时 | 实时 | §3.9 |

> `Effect.readout = "per_path"` 就是按这张表分派；不能再给一个全局单一读数。

**白板常数**：`K = 0.454545… × 1.0 × 2.5 = 1.136363…`。报告必须同时给
`absoluteDamage`（乘 K）与 `relative`（除基准），否则「总伤」与「百分比」必有一个是错的。

### 28.3 Effect 目标注册表、条件与叠加

#### 28.3.1 目标注册表（白名单，未知即报错）

| `target` | `kind` | 作用方式 | 适用路径 | 读数 |
| --- | --- | --- | --- | --- |
| `atk_pct` / `atk_flat` | pct / flat | 战斗攻击白值 | 全部 | per_path |
| `hp_pct` / `hp_flat` / `def_pct` / `def_flat` | pct / flat | 生命 / 防御白值 | 全部 | per_path |
| `cr` / `cd` | pct | 常规暴击区 | 直伤（锋御用锐暴） | realtime |
| `dmg` | pct | 增伤区加算；按 `damageType` 过滤 | 全部 | per_path |
| `am` | flat | 异常精通 | 异常（直伤不吃） | snapshot |
| `pr` / `pv` | pct / flat | 穿透率 / 穿透值 | 全部 | per_path |
| `anomaly_dmg` | pct | 异常增伤区加算 | 异常 / 紊乱 / 异放 / 乱流 | realtime |
| `anomaly_crit_rate` / `anomaly_crit_dmg` | pct | 异常暴击区 | 异常 / 紊乱 / 异放 / 乱流 | realtime |
| `resistance_reduce` | pct | 抗性区加算 | 全部 | realtime |
| `ignore_defense` | pct | 与减防加算，进防御区 | 全部（命破防御区恒 1） | realtime |
| `defense_reduce` | pct | 敌方减防 debuff；与 `ignore_defense` 加算 | 全部 | realtime |
| `ignore_resistance` | pct | 抗性区加算 | 全部 | realtime |
| `stun_vulnerability` | pct | 失衡易伤**倍率**加算 | 全部 | realtime |
| `special` | pct | 独立特殊乘区 | 全部 | realtime |
| `blast_damage` | pct | 锐暴伤害加成（锋御）；加到基础 150% 上 | 锋御直伤 | realtime |
| `direct_dmg_mult` | pct | 直伤独立倍率区 | 直伤 | realtime |
| `skill_multiplier_bonus` | pct | 事件倍率加算 | 全部 | snapshot |
| `impact_pct` | pct | 冲击力 | **不进入伤害**（白板不评价） | n/a |
| `energy_regen` / `anomaly_control` | pct / flat | 能量 / 掌控 | **不进入伤害**；只影响循环假设 | n/a |

规则：

- `mode = additive` 的目标（`dmg` / `anomaly_dmg` / `am` / `pr` / `pv` / `resistance_reduce` /
  `ignore_defense` / `ignore_resistance` / `stun_vulnerability` / 暴击双围）按**同区相加**；
- `special` / `direct_dmg_mult` 是**独立乘区**，不参与加算；
- 未知 `target` → **拒绝加载**，不做静默忽略；
- `impact_pct` / `energy_regen` / `anomaly_control` 若出现在伤害报告里，`status` 必须是
  `descriptive`，并写明「本口径不评价」。
- `special` / `direct_dmg_mult` / `skill_multiplier_bonus` 在 v1 **先预留**：若试点角色
  需要，P1 一并实现对应乘区；否则使用它们的条目必须标 `descriptive`，
  **不得**静默当 0 或塞进普通增伤区。
- **锋御特例**：`cr` 效果直接加到 `actual_cr`；`cd` 效果**不参与**「初始暴伤 → 暴击率」
  转模（只有初始暴伤参与）；`blast_damage` 效果加到基础 150% 上，再进平方项暴击区。

#### 28.3.2 伤害类型过滤

`damageType` 允许字符串或数组，加载时统一成数组：

```text
all                  → 所有事件
fire/ice/...         → 该属性的事件 + 该属性的属性异常
direct               → path ∈ {normal, piercing, armorer}
anomaly              → path ∈ {anomaly, disorder, release, turbulence}
basic/special/...    → event.tags 包含该标签
```

匹配规则：**任一** `damageType` 命中即生效；`all` 命中一切。火伤加成不得打到物理事件；
异常增伤不得打到直伤事件。

> 事件侧的 `damageType` 写**元素**（`fire` / `ice` / …）；`direct` / `anomaly` 只是
> effect 侧的**过滤选择器**，不要写进事件。事件属于直伤还是异常，由 `path` 决定。

#### 28.3.3 条件 DSL

`condition` 只允许下列形式（可嵌套 `and` / `or` / `not`）：

| 条件 | 真值 |
| --- | --- |
| `always` | 恒真 |
| `enemy_stunned` | 目标处于失衡（白板恒真） |
| `enemy_under_anomaly` + `element` | 目标有该属性异常 |
| `enemy_under_state` + `state` | 目标有指定状态（如 `zhuoshi` / `burn`） |
| `self_has_state` + `state` | 自身有指定状态（如 `sheng_bian`） |
| `on_skill` + `skill`/`tags` | 当前事件是 / 含指定技能标签 |
| `on_ex` / `on_ultimate` / `on_special` | 当前事件是强化特殊技 / 终结技 / 特殊技 |
| `on_anomaly_crit` | 本次异常暴击 |
| `on_anomaly_applied` | 本次施加了属性异常（用于叠层类音擎） |
| `any_ally_anomaly_crit` | 队伍中任意角色（含自己）的属性异常伤害产生暴击 |
| `on_field` | 装备者处于前场；v1 默认 true（主 C 口径） |
| `wielder_attribute` + `value` | 装备者属性匹配（如以太音擎对火角色为假） |
| `wielder_role` + `value` | 装备者定位匹配（强攻 / 异常 / 命破 / 锋御 / …） |
| `team_has` + `agentId`/`element` | 队伍中有指定角色 / 属性；**自己也算队伍成员** |
| `stacks_at_least` + `n` | 指定层数 ≥ n |

**求值上下文**必须包含：事件标签、目标状态、自身状态、层数、队伍、面板属性。
条件为假 → 效果为 0；条件未知 → **报错**，不能当假。
`condition` 允许**字符串**（等价于 `{ "kind": "..." }`）或**对象**；带参数的条件
（如 `enemy_under_state` 的 `state`）必须用对象。加载后统一归一化成对象。
`team_has` 在没有队友时只检查自己；若自己也无法满足（如「以太属性的装备者」对火角色），
条件为假，不能靠 `uptime` 硬开——除非报告显式写 `teamMode: "team"` 与对应队友。

#### 28.3.4 层数、覆盖率与叠加

```text
effective = base
if perStack: effective *= stacks.expected
effective *= uptime          # 0..1
if not condition: effective = 0
```

补充字段规则：

- `id` 在同一个 `calculator.json` 内唯一；重复 → 拒绝。
- `scope` 只允许 `self` / `team`；v1 **只支持 `self`**。`team` 需要冻结快照，
  且 `assumptions.teamMode` 必须是 `"team"`；否则拒绝，不能悄悄按自己算。
- `phase: "out_of_combat"` 只保留给「必须在面板前生效」的少量数据；
  音擎 `base` / `substat`、核心 `base` 走 `PanelRequest`，**不要**重复放进 `effects`。
- `duration` / `refresh` 在 v1 只是**元数据**：v1 没有时间轴，覆盖率由作者填
  `uptime`；v2 才用它们算 Buff 窗口。不要因为写了 `duration` 就自动假设 100% 覆盖。
- 层数的获得 / 重置 / 掉层**不模拟**；v1 用 `stacks.expected` 的平均值，v2 时间轴再算。
- `uptime` 在 `condition` **之后**生效：条件为假时，`uptime` 不能把它变成真。
  需要「队伍条件恒真」时，写 `assumptions.teamMode: "team"` + 对应队友，
  不能只把 `uptime` 填 1.0。
- `stackGroup` 可选；同组效果先按组规则取最大/相加，再进累加器；跨组相加。
- `stacks.expected` 可以是小数（期望层数）；`stacks.max` 是上限；`stacks.default` 是默认值。
  `perStack: false` 时 `stacks` 不参与乘法，只用于展示。
- `uptime` 是**期望覆盖率**；默认值必须有来源（`source` 或 `notes`），不能裸填 1.0。
- `status = modeled` 要求 `value` / `perRefinement`、`condition`、`stacks`、`uptime` 都已确定；
  任何一项缺失 → `partial`；完全没数值 → `descriptive`。
- `not_applicable` 表示**条件确定不满足**（如以太音擎对火角色、`[异常]` 音擎对强攻）；
  它贡献 0，但不是「未建模」，报告写「不适用」并说明条件。
- 报告必须给 `coverage.modeledDamageShare`：已建模效果覆盖的伤害事件份额；
  `partial` 的变体不能与 `modeled` 变体直接排名。

  计算口径：某事件如果被任何 `descriptive` / `partial` 且 `damageType` 命中的效果影响，
  该事件记为「未完全建模」；`modeledDamageShare = ΣD(完全建模事件) / ΣD(全部事件)`。
  条件为假的效果不算「影响」。这是**保守**口径，宁可低估覆盖率。

**`value` 与 `perRefinement` 二选一**：

- 有 `perRefinement` 时必须长度为 5，按 `R1..R5` 取下标；
- 同时写 `value` 和 `perRefinement` → 拒绝；
- `perStack` 只影响 `value` / `perRefinement` 的最终值，不改变数组长度。

### 28.4 Event / Rotation 完整契约

#### 28.4.1 事件字段

| 字段 | 必填 | 类型 | 说明 |
| --- | --- | --- | --- |
| `id` | 是 | string | 唯一；报告按它聚合 |
| `label` | 是 | string | 展示名 |
| `owner` | 是 | agentId | 招式持有者；队友事件写队友 id |

| `multiplier` | 是 | number | **百分数**；加载时 `/100` |

| `tags` | 否 | string[] | 技能类型、攻击类型、机制标签 |
| `critMode` | 否 | 枚举 | `expected`（默认）/ `crit` / `non_crit` |

| `duration` | 否 | number | 事件时长（秒）；v2 时间轴用 |
| `energyCost` / `energyGain` | 否 | number | v1 **不参与**；只登记，报告标 `descriptive` |
| `condition` | 否 | DSL | 事件级条件；假则跳过 |
| `anomaly` / `disorder` / `release` / `turbulence` | 否 | object | 路径专属块，见下 |

> v1 的 `startTime` / `duration` 只登记、不参与计算；`assumptions.timeline` 必须是
> `"none"`。写 `timeline: "event"` 直接拒绝——时间轴是 v2 的事，不能半实现。

#### 28.4.2 路径专属块

```jsonc
"anomaly": {
  "multiplier": 1250,      // 单次异常倍率（百分数）；事件 multiplier 必须为 1.0
  "base": "fire",           // 基底属性
  "elapsed": 0,             // 可省略；紊乱/乱流用
  "duration": 10            // 可省略；用于有效持续时间
},
"disorder": {
  "base": "fire",
  "elapsed": 2,             // t，已流逝秒数
  "multiplier": null        // null = 按 §6.1 表解析；非 null 时直接使用
},
"release": {
  "sourceAgent": "ep-2216",
  "baseAnomaly": "fire",
  "mode": "fixed",          // fixed | original
  "multiplier": 600
},
"turbulence": {
  "base": "fire",
  "remainingSeconds": 8     // T
}
```

规则：

- `anomaly` / `disorder` / `turbulence` 的 `multiplier` 是**伤害倍率**，不是失衡倍率；
  紊乱的失衡 200% 单独在 §10 处理。
- `disorder.multiplier = null` 时，按 §6.1 的 `450% + 时间项` 解析；`elapsed` 必须在
  `[0, 有效持续时间]`，否则报错，不静默夹紧。
- `release` 必须是**来源 / 触发者分离**的：`sourceAgent` 只提供原异常与异化，触发者侧
  不得重复乘异化乘区；v1 不实现，但 schema 先固定。
- `turbulence` 的 `remainingSeconds` 就是 §12 的 `T`，不是 `t`。
- `disorder` / `turbulence` / `release` 每个事件只表示**一次结算**；不同 `elapsed` /
  `remainingSeconds` 拆成多个事件。`count > 1` 只允许在时间参数完全相同时使用。
- 事件 `multiplier` 与块内 `multiplier` 的单位必须一致（都是百分数）；加载时只除一次。

#### 28.4.3 倍率表的数据形状

`<slug>.json` 的 `growth` 解析后，统一成：

```jsonc
{
  "agentId": "ep-2216",
  "sourceSha256": "…",
  "levels": {
    "普通攻击：裁生": {
      "damage":  { "1": { "一段": 15.6, "二段": 67.7 }, "…": {} },
      "stagger": { "1": { "一段": 13.2, "二段": 45.5 }, "…": {} },
      "release": { "1": { "": 525 }, "…": {} }
    }
  }
}
```

- `damage` / `stagger` / `release` 分开；不要把失衡倍率混进伤害倍率。
- 单行倍率（如「伤害倍率：1294.3%」）的 segment key 用 `""`。
- 多段招式：`multiplier` 取**所选段之和**；只打部分段时，拆成多个事件，不要用总倍率。
- `skillLevel = 基础等级 + 影画 C3/C5 的 +2 + 核心技 +1`；超过表上限 → 标
  `unsupported`，**不外推**。
- 解析失败 / 重复 / 非数字 → 报错，不猜、不跳过。

#### 28.4.4 循环校验

| 检查 | 规则 |
| --- | --- |
| id | 唯一 |
| 次数 | `hits ≥ 1`、`count ≥ 1`、`hits × count` 为正整数 |
| 倍率 | `multiplier > 0`；异常/紊乱/乱流事件的事件倍率必须为 `1.0` |
| 路径块 | `path` 与必填块匹配；不得同时出现两个块 |
| 路径 / `scaling` | `piercing` 必须 `penforce`；`armorer` 必须 `def`；`normal` / `anomaly` / `release` / `turbulence` 必须 `atk` |
| `critMode` | 锋御 `armorer` 只支持 `expected`；`crit` / `non_crit` 拒绝（引擎未实现锐暴的单次模式） |
| 招式 | `move` 必须在倍率表中存在 |
| 覆盖率 | `modeledDamageShare ≥ 0.95` 才能标 `complete`；否则 `partial` 并列出未覆盖项 |
| 时长 | `rotationSeconds > 0`；每秒伤害只在同一代理人内比较 |
| 能量 | v1 不校验；`energyCost`/`energyGain` 只登记 |

`rotationPatches` 支持 `add` / `set` / `remove` / `scale`，按影画等级升序应用；
同一事件同一字段被多次修改时**后者胜出**并记一条 warning；不得删除基线事件后
让 `count` 变成负数。

#### 28.5.4 `assumptions`、`status` 与版本

```jsonc
"assumptions": {

  "rotationSeconds": 20,
  "stacks": { "ep-212": 2, "ep-214": 1 },   // 每把武器的默认期望层数
  "uptime": { "weapon.ep-2259.passive.fire_dmg": 1.0 },
  "timeline": "none"               // v1 固定 none；v2 才允许 "event"
}
```

| 字段 | 规则 |
| --- | --- |
| `teamMode` | `solo` 时 `scope: team` 的效果 / `team_has` 条件只查自己；不满足即为假 |
| `critMode` | 默认 `expected`；`crit` / `non_crit` 只用于展示，不用于优化排序 |
| `onField` | 默认 `true`；`false` 时所有 `on_field` 条件为假 |
| `rotationSeconds` | > 0；只用于每秒伤害，不参与排序 |
| `stacks` | key 为音擎 id；值必须在 `[0, max]`；缺省用 `stacks.default` |
| `uptime` | key 为 effect id；值在 `[0,1]`；缺省按 `stacks` / 条件求值 |
| `timeline` | v1 必须为 `"none"`；写 `"event"` 直接拒绝 |
| `sensitivity` | 可选；key 为 `stacks:<weaponId>` / `event:<eventId>.<field>`，值为候选数组；报告生成敏感性表 |

- `status`：`draft` / `partial` / `complete`；只有 `complete` 才允许作为「已发布」。
- `engineVersion`：声明兼容的引擎版本区间；超出拒绝加载。
- `substatCaps`：可省略；给了就必须**等于** §28.5.3 推导值，否则拒绝（防手填漂移）。
- `mainStats`：必须是规则表里的合法 id；1/2/3 号位固定，不写。

### 28.6 Optimizer 完整契约

#### 28.6.1 变量与目标

```text
默认：只优化副词条档数 n_i，主词条/套装/音擎/影画固定
可选：mode = "main+sub" 时，先枚举 4/5/6 主词条组合（6×5×6 = 180），再对每组优化 n
目标：maximize D(n) = Σ_event damage(event, combat(panel(n), effects), target)
约束：Σ n_i = N；0 ≤ n_i ≤ cap_i；n 在 6 个盘上可行（§28.6.2）
```

`D(n)` 用完整局内伤害；不得用面板代理分。不同 `N` 的曲线必须由**同一优化器**重跑，
不能用「从满配往下拆」代替 `optimal`。

#### 28.6.2 每盘可行性判定（可实现步骤）

```text
输入：n_i（10 个整数），主词条排除表
1. 快速剪枝：
   - Σ n_i = N；n_i ≤ cap_i
   - Σ ceil(n_i / 6) ≤ 24
2. 分配盘位 d_i：
   - 下界 d_i^min = ceil(n_i / 6)
   - 上界 d_i^max = min(6 − excluded_i, n_i)
   - 需要 Σ d_i = 24
   - 先取 d_i = d_i^min，再按剩余额度把 d_i 加到上界
3. 二部图匹配（max-flow）：
   source → stat i（容量 d_i）
   stat i → disc j（容量 1；主词条排除的 j 不连边）
   disc j → sink（容量 4）
   要求最大流 = 24
4. 分配档数：
   - 每个被分配的 (i, j) 先给 1 档（共 24 档）
   - 剩余 N − 24 档是强化；每个盘最多 5 档，每条最多 5 档
   - 对每个盘，用一次小流/贪心分配 5 档，使 Σ_j x_ij = n_i
5. 任一步失败 → infeasible；报告给出失败原因（是 cap、盘位还是强化额度）
```

> 只用 `Σ n = 54` + `n_i ≤ 36` 会给出 `AM 27 + ATK% 27` 这种刷不出来的解；
> 第 3–4 步就是拦住它的地方。不要用「平均每条 4.5 档」这种近似替代。

#### 28.6.3 搜索参数（默认值）

| 参数 | 默认 | 说明 |
| --- | ---: | --- |
| `threshold` | 0.0 | 预筛门槛；0 = 只丢非正收益 |
| `topNPerGroup` | 4 | 每组兜底保留，防「终局值钱」被误杀 |
| `coarseStep` | 3 | 粗搜步长 |
| `beamWidthCoarse` | 64 | 粗搜每层保留 |
| `beamWidthFine` | 256 | 细搜每层保留 |
| `topK` | 8 | 进入局部搜索的候选数 |
| `localSearch` | `1-swap` + `2-swap` | 1-swap 全部，2-swap 只对 Top 3 |
| `maxEvaluations` | 200000 | 刹车；打满标 `budgetHit` |
| `timeLimitSeconds` | 300 | 单预算上限 |
| `tieBreak` | 字典序 | 分数相同按 allocation 升序 |

#### 28.6.4 输出与验证

```jsonc
{
  "budget": 54,
  "mode": "substats",
  "allocation": { "am": 30, "atk_pct": 11, "atk_flat": 6, "pen_val": 6, "hp_pct": 1 },
  "feasible": true,
  "damage": { "total": 60713.49, "byPath": { "anomaly": 60713.49 } },
  "search": { "algorithm": "two-stage-beam+local", "evaluations": 138240, "budgetHit": false },
  "warnings": []
}
```

验收：

- `N ≤ 12` 时与全枚举最优**逐 allocation 相等**（同分同字典序）；
- 所有输出过 §28.6.2；
- `D(N+1) ≥ D(N)`（重优化后）；
- 固定输入两次生成字节一致（除时间戳）；
- 单代理人 7 档预算（54/45/40/35/30/25/20）总耗时 ≤ 8 分钟（单核目标；超时只允许降 beam，不允许改口径）。

### 28.7 驱动盘评分与相对值的完整契约

#### 28.7.1 评分锚点

`w_i` 必须带锚点，不能给「永久有效」的权重表：

| 锚点 | 用于 | 说明 |
| --- | --- | --- |
| `current` | 我现在的这套配装 | 用当前面板 + 当前循环算 `w_i` |
| `graduation` | 交易/对比/攻略页 | 用该代理人 54 条最优面板 + 基准循环算 `w_i` |

报告必须写 `scoreAnchor: "current" | "graduation"`；跨锚点的分数不可比。

#### 28.7.2 三个分数，不要混

```text
w_i = D(n + e_i) − D(n)                  # 单档边际；n_i 达 cap 时记 0
S_disc = 100 × Σ r_i w_i / (6w1 + w2 + w3 + w4)   # 副词条分，0–100
S_main = 100 × (main_value_in_rolls × w_main) / (10w1)  # 主词条分，0–100
damageRatio = D(装该盘) / D(装该槽完美盘)          # 权威比较，0–1
```

- `S_disc` 只评价副词条；`S_main` 只评价主词条；**不要把两者相加**成一个「总分」。
- `w_i` 计算后 clamp 到 **≥ 0**；负收益（条件性减益）不参与评分，只在 `notes` 里说明。
- `damageRatio` 是唯一可用于「A 盘 vs B 盘」的排序依据；`S_disc` 只用于解释「为什么」。
- 完美盘定义：该槽位主词条取当前最优，4 条副词条按 `6w1 + w2 + w3 + w4` 分配。
- 套装效果不计入单盘分；套装收益单独给 `setScore` / `setNote`。

#### 28.7.3 有效性与阈值

| 判定 | 条件 | 展示 |
| --- | --- | --- |
| `dead` | `w_i = 0` | 灰色「无效」 |
| `low` | `0 < w_i < 0.1 × w_max` | 「低效」 |
| `effective` | `0.1 × w_max ≤ w_i < 0.5 × w_max` | 「有效」 |
| `core` | `w_i ≥ 0.5 × w_max` | 「核心」 |

阈值是**展示分层**，不是优化器剪枝条件；优化器只按真实 `D(n)` 排序。
`w_i` 在 `n_i = cap_i` 时为 0；在暴击帽/穿透下限之后也为 0。

#### 28.7.4 相对值口径

| 项 | 固定值 |
| --- | --- |
| 基准 | `C0R1`：0 影画 + 专武 R1 |
| 基准面板 | 54 条**最优**副词条（§21），主词条/套装/核心固定 |
| 循环 | `calculator.json` 的基准循环；所有变体同一循环，除非影画 `rotationPatches` 显式修改 |
| `samePanel` | **同一套副词条分配**；换武器/影画后基础值/副词条数值会变，totals 允许变 |
| `optimalPanel` | 每个变体重新跑 §21，只重优化副词条；主词条/套装不变 |
| 标题数字 | `optimalPanel` |
| 解释数字 | `samePanel` |
| 取整 | 相对值 2 位小数；`100.00` 为基准 |
| 影画累计 | C2 包含 C1；C6 包含 C1–C6 |
| 武器变体 | 推荐音擎 × R1–R5；A 级武器同样 5 档 |
| 矩阵 | 行 = 影画 C0–C6，列 = 音擎/精炼；基准格 = C0R1 |

**v1 固定发布预算**：`54 / 45 / 40 / 35 / 30 / 25 / 20`。报告和策略页只展示这 7 档；
其它预算可用于临时分析，但不进正式表。`54` 是满配，`30` 是非满配锚点。

**状态聚合规则**：

- `modeled`：所有 effect / cinema 效果都 `modeled`，且 `modeledDamageShare ≥ 0.95`；
- `partial`：有 `partial` 或 `descriptive` 项，或覆盖率 < 0.95；
- `partial` 的相对值**可以显示**，但必须带 `*` 与「未建模项」列表，**不得**与 `modeled`
  变体直接排名；
- `descriptive` 变体不给相对值，只显示「未计入」。

### 28.8 数据管线与裁决

#### 28.8.1 音擎 effect 的最终形状

```jsonc
"effect": {
  "schemaVersion": 1,
  "name": "破壳日",
  "tag": "异常",
  "raw": "官方原文…",
  "source": "https://baike.mihoyo.com/zzz/wiki/content/2259/detail",
  "scrapedAt": "2026-10-23T…",
  "targets": [
    {
      "target": "am", "kind": "flat",
      "perRefinement": [90, 99, 108, 117, 126],
      "phase": "in_combat", "readout": "per_path",
      "status": "modeled"
    }
  ],
  "status": "modeled"
}
```

- `raw` 必须逐字保留；数值映射是**人工/评审**结果，不自动猜。
- `effect.tag`（如 `[异常]` / `[命破]`）必须转成 `targets[].condition: wielder_role`；
  不能只展示。off-role 角色可以装备该音擎（基础值/副词条仍生效），但被动为 0。
- `targets[].status` 与 `effect.status` 同时存在时，取更保守的那个
  （`descriptive` > `partial` > `modeled`）。
- 抓取脚本只负责 `raw` + 面板 + 精炼数组的**候选**；`targets` 初始为空、
  `status: "descriptive"`，评审后才升 `modeled`。

#### 28.8.2 其他数据

| 数据 | 位置 | 规则 |
| --- | --- | --- |
| 影画 | `calculator.json` 的 `cinema[]` | 手工；带 `sourceTextHash`；文本变 → 标「需复核」 |
| 技能倍率 | `strategy/<slug>/calculator/multipliers.json` | 生成物；带 `sourceSha256`；`--check` 比对 |
| 4 件套 | `data/catalog/drive-discs.json` 的 `effect4` | 与 `effect2` 同模式；未映射写 `null` + `effect4Note` |
| 逐角色机制 | 拟新增 data/catalog/agent-mechanics.json | 手工；字段见下 |

`agent-mechanics.json` 的最小形状：

```jsonc
[
  {
    "agentId": "ep-2145",
    "armorerBlastDamage": 150,      // 锋御锐暴基础；默认 150
    "armorerCritFromCd": 0.35,      // 初始暴伤→暴击率；默认 0.35
    "anomalyCritRateBase": 0,       // 异常暴击率基础；0 = 不额外加成
    "anomalyCritDmgBase": 0,        // 异常暴伤基础；0 = 不额外加成
    "notes": "…"
  }
]
```

字段缺失时用默认值；出现未知字段 → 拒绝。`agentId` 必须存在于 `agents.json`。

`drive-discs.json` 的 4 件套：

```jsonc
"effect4": {
  "status": "modeled",           // modeled | descriptive | null
  "targets": [ /* 与 Effect.targets 同形状 */ ],
  "note": "条件：强化特殊技命中后…"
}
```

- `effect2` 保持现有「字符串 id」不变；`effect4` 因为几乎都是条件触发，用结构化对象。
- 未建模时写 `"effect4": null` + `effect4Note`，**不要**用一个假 id 占位。
- 同一套装的 4 件套效果只生效一次；6 件同套时仍是「1 个 4 件套 + 1 个 2 件套」，
  不叠加 2 件套。

**属性伤害 2 件套**（`drive-discs.json` 里 `effect2Note: "属性伤害"` 的那些）：

- 它们**不进面板**（面板没有元素行，硬加会破坏三方对拍）；
- 在 `calculator.effects` 里补一条 `dmg +10`、`damageType: <套装元素>`；
- 套装元素 ≠ `build.dmgElement` → `not_applicable`，不是 0 收益悄悄吞掉；
- 这样 14 套属性伤害 2 件套能在伤害层被算到，同时不碰面板对拍。
| 目标 | `core/damage/targets.py` | 白板 + 敏感性目标；不进 `calculator-rules.json`（规则表只放配装选项） |
